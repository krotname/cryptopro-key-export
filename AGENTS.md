# AGENTS.md — контекст для LLM-агента

Инструкции для любого агента (Claude Code, Codex, Cursor …), продолжающего этот проект.
Прочитай также `README.md` (что делает проект) и `ROADMAP.md` (что делать дальше).

## Назначение проекта
Инструмент для **владельца собственных ключей ЭЦП**: снять ключевой контейнер КриптоПро
с Рутокена и снять запрет на экспорт закрытого ключа (резервная копия / миграция / PFX).
Легитимный сценарий — работа пользователя со своими сертификатами. Не добавляй функций,
рассчитанных на чужие ключи или обход чужих ограничений.

## Стек
- .NET `net10.0-windows`, C#. Нужен .NET SDK 10. Решение — `CryptoProExport.slnx` (новый XML-формат; не удивляйся отсутствию `.sln`).
- `CryptoProExport.Core` — библиотека (COM/CryptoAPI/процессы). `CryptoProExport.App` — WinForms + CLI. `tests/CryptoProExport.Tests` — xunit.
- **Внешние NuGet-пакеты в Core и App разрешены** (решение владельца от 06.08.2026; прежний запрет снят — он закрывал ГОСТ-криптографию и PKCS#11). В Core один пакет — `Pkcs11Interop` 5.3.0 (чисто managed, netstandard2.0; путь для Рутокен ЭЦП/Lite, см. `Pkcs11Token`); нативная `rtPKCS11ECP.dll` берётся из системы, не вшивается. В тестах — `xunit` 2.9.3, `xunit.runner.visualstudio` 3.1.5, `Microsoft.NET.Test.Sdk` 18.8.1. Добавляя пакет, помни о цене: размер портативного exe и цепочка поставки. Следующий вероятный кандидат — BouncyCastle (ГОСТ), см. ROADMAP P1.
- **Разрядность x86 по умолчанию** (`PlatformTarget` в `CryptoProExport.App.csproj`, условие снимается при явном `-r`). Причина ниже; x86 при этом универсален — идёт и на x64, и на ARM64.
- **Лицензирование (v1.6.0).** Операции экспорта закрытого ключа (`export`, `tokenexport`, `tokenfull`, `full`, `keyexport`, `extractkey`, `extractpfx`, `liteexport`, `topfx`) закрыты **жёстким гейтом** `LicenseGate` (Core): нужен подписанный файл лицензии продукта `cryptoexport` от сервера активации **`krotname/license-server`**, проверяется **офлайн** вшитым публичным ключом (ES256, `kid=cryptoexport-2026`, отпечаток `sha256:93cd9447…`). Диагностика/справка/установка лицензии — свободны. Референс-клиент проверки **вендорнут** в `src/Core/Licensing/{LicenseVerifier,LicenseModels,ActivationCode}.cs`: **источник правды — `license-server/clients/dotnet`**, кросс-репо `ProjectReference` не собрался бы на CI, поэтому здесь копия (помечена `#nullable enable`, не редактировать вручную; при изменении протокола правится сначала license-server, затем синхронизируется сюда). Отпечаток машины — `LicenseGate.Fingerprint()` = `sha256:<hex>` от MachineGuid (реестр, `RegistryView.Registry64` для x86 в WOW64); сырой идентификатор не логируется. Команды CLI `fingerprint`/`license [file|status]`, кнопка «Лицензия…», статус в логе при запуске. 14 ключей i18n × 20 языков (`license.*`, `cli.usage.fingerprint/license`, `btn.license`, `tip.license`, `dlg.license.title`). Лицензия установлена в `%LOCALAPPDATA%\CryptoProExport\license.jws`. Выпуск тестовых/ручных лицензий пока офлайн: `keytool issue-license` в license-server (REST `/v1/activate` там ещё не развёрнут).

## Внешние зависимости
- **КриптоПро CSP** — единственное, что ставится на целевой машине отдельно (лицензионный продукт; CryptoAPI и `p12utility` завязаны на него).
- **`p12utility.win32.exe`** и **`rtCOMLite.dll`** лежат в `tools/`, **вшиваются в `CryptoProExport.Core` как embedded resources** (см. `.csproj`) и распаковываются в `%LOCALAPPDATA%\CryptoProExport\bundled\<версия>` при первом обращении (`BundledTools`). Доставлять их отдельно не нужно.
- `rtCOMLite.dll` (COM `rtCOMLite.rtContext`, CLSID `{0ACACF07-…}`) создаётся **без регистрации в системе**: `NativeLibrary.Load` → `DllGetClassObject` → `IClassFactory::CreateInstance` (`RegFreeCom`). Запасной путь — зарегистрированный в системе компонент (ProgID), если он есть.
- Условие `Exists(...)` в `.csproj` позволяет собрать репозиторий и без бинарников в `tools/` — приложение тогда честно сообщит, что зависимость не вшита.

## Сборка и тесты
```bash
dotnet build CryptoProExport.slnx -c Release -warnaserror   # 0 ошибок, 0 предупреждений
dotnet test  CryptoProExport.slnx -c Release --no-build     # 480 тестов xunit
```
Тесты покрывают чистую логику: кодеки cp1251/cp866, `name.key`, аргументы p12utility,
разбор разрядности PE, наличие вшитых зависимостей, `ContainerStore` (во временной папке —
системное хранилище КриптоПро не трогается), классификацию токена по модели PKCS#11 и мягкую
деградацию `Pkcs11Token` без токена/драйвера.
Проверка без физического токена (обязательный минимум перед коммитом):
```powershell
# ВАЖНО: .exe запускать только через PowerShell Start-Process; из git-bash — "Permission denied".
# WinExe печатает в stdout ТОЛЬКО при перенаправлении в файл. Вывод в UTF-8:
#   [Text.Encoding]::UTF8.GetString([IO.File]::ReadAllBytes("$PWD\st.txt"))
$exe = "src\App\bin\Release\net8.0-windows\CryptoProExport.exe"
Start-Process $exe "--selftest" -Wait -RedirectStandardOutput st.txt -WindowStyle Hidden   # SELFTEST OK + отчёт о зависимостях
Start-Process $exe "deps"       -Wait -RedirectStandardOutput dp.txt -WindowStyle Hidden   # откуда берутся зависимости
Start-Process $exe "list"       -Wait -RedirectStandardOutput ls.txt -WindowStyle Hidden   # перечень контейнеров
```
`--selftest` заодно проверяет, что у всех кнопок/полей/списков проставлены всплывающие подсказки
(`MainForm.CheckTooltips`), и падает с кодом 1, если появился элемент без подсказки. Форма при этом
строится на **каждом** вшитом языке, и вторая проверка (`MainForm.MissingTranslations`) ловит
незаполненные ключи перевода — они видны как `[!ключ!]`.

Портативная сборка (один exe, всё внутри):
```powershell
pwsh build\publish.ps1           # publish\CryptoProExport.exe, ~44 МБ, других файлов в папке нет
pwsh build\publish-remote.ps1    # то же, но собирает домашний Ubuntu-сервер (ubuntu-xeon)
```
Сборка на Linux работает благодаря `EnableWindowsTargeting` в csproj: SDK берёт
reference-пакеты Windows Desktop из NuGet. Компилируется там всё, включая WinForms;
запускать и тестировать по-прежнему нужно на Windows. На сервере стоит `dotnet-sdk-10.0`
из штатного репозитория Ubuntu, исходники уезжают tar-потоком по SSH (rsync на Windows нет),
готовый exe возвращается по scp и сверяется по SHA-256.

**Тестовые файлы с личными данными.** Перенаправленный вывод (`st.txt`, `ls.txt`, …) содержит
имена контейнеров с ФИО — удаляй сразу после проверки, не коммить.

## Тестовый контейнер без персданных
Для проверки цикла «снятие запрета → установка в CSP → PFX» не нужен ни токен, ни живой ключ:
```powershell
$csptest = "C:\Program Files\Crypto Pro\CSP\csptest.exe"
& $csptest -keyset -newkeyset -container "\\.\HDIMAGE\cpxtest" -provtype 80 -protected=none
& $csptest -keyset -container "\\.\HDIMAGE\cpxtest" -provtype 80 -makecert   # самоподписанный серт в контейнер
```
Появится `%LOCALAPPDATA%\Crypto Pro\cpxtest.000` с шестью `*.key` и сертификатом внутри
(CN=cpxtest). Дальше: `extractcert` → копия папки → `keyexport` → `install` → `checkexport` → `topfx`.
Убирать за собой: `csptest -keyset -deletekeyset -container …` или удалить папку и снять
сертификат из хранилища «Личное».

## CI
GitHub Actions **работает** (`.github/workflows/ci.yml`). Прежнее утверждение,
что Actions заблокированы биллингом, не подтвердилось — прогоны идут. Три job:
- `build` — сборка с `-warnaserror`, тесты, портативная сборка с `--selftest`, проверка отчёта
  о зависимостях, проверка встроенного руководства, контроль «в publish ровно
  один файл», SHA-256, артефакт с exe и суммой;
- `architectures` — матрица `win-x64`/`win-arm64`: только публикация, чтобы ловить регрессии
  компиляции под другие RID;
- `release` — по тегу `v*` создаёт GitHub Release с портативным exe и контрольной суммой.

**Релиз публикуется через REST API (`curl`), а не через `gh`.** На собственном Linux-раннере
`adler` GitHub CLI не установлен, и шаг падал на каждом теге (`gh: command not found`, код 127);
релиз v1.3.1 выкладывали руками. `curl` и coreutils есть везде, поэтому шаг больше не зависит от
предустановленных инструментов. Две тонкости, на которых он уже ломался при отладке:
`upload_url` в ответе — URI-шаблон `…/assets{?name,label}`, хвост `{...}` надо отбросить, и
разбивать ответ по запятым нельзя — шаблон сам содержит запятую; при `set -euo pipefail` пустой
`grep` убивает шаг молча, поэтому у извлечения стоит `|| true` и явная проверка с сообщением.

**Раннеры.** Windows-job'ы (`build`, `architectures`) идут на собственном раннере
`adler-white-1w-cryptopro` — служба на домашнем сервере ADLER-WHITE-1W, каталог
`C:\actions-runner-cryptopro`, метки `self-hosted,Windows,X64,adler-white-1w,cryptopro`.
**Это целевой сборщик проекта**: продукт — Windows (WinForms + CryptoAPI, `net10.0-windows`),
и полная валидация (юнит-тесты, `--selftest`, `deps`, коды CLI) возможна только на Windows.
Ушли с `windows-latest`, потому что минуты Windows списываются из квоты Pro с коэффициентом ×2.
`release` остаётся на Linux-раннере брокера (`adler`). Пути отхода: переменные репозитория
`CI_RUNS_ON_WINDOWS` (`["windows-latest"]`) и `CI_RUNS_ON` (`["ubuntu-latest"]`) — они разные,
значения несовместимы.

**Резерв — домашний Linux-раннер `adler-ubuntu-xeon`** (метки `self-hosted,Linux,adler-ubuntu-xeon`,
всегда включён). На Linux компилируется весь проект, включая WinForms (`EnableWindowsTargeting`),
и собирается портативный exe — этим он и полезен для ручной сборки (`build\publish-remote.ps1`).
**Но автоматическим фолбэком CI он не является**: job'ы `build`/`architectures` в текущем `ci.yml`
читают только `CI_RUNS_ON_WINDOWS` (не `CI_RUNS_ON` — тот влияет лишь на Linux-job `release`), а
сами шаги `build` завязаны на Windows (pwsh, `Start-Process` над exe, чтение реестра в `deps`),
так что на Linux-раннере они бы просто упали. Единственный автоматический фолбэк для
`build`/`architectures` — `CI_RUNS_ON_WINDOWS=["windows-latest"]` (hosted Windows, ×2 минуты).
Чтобы CI реально шёл на Ubuntu, нужно переструктурировать `build` под Linux (compile/publish без
запуска exe и с рантайм-тестами в отдельном Windows-job'е) — так было в PR #32/#34, но решение
владельца — держать целевым сборщиком Windows-раннер, а Ubuntu Xeon оставить резервом ручной
сборки. Причина: WinForms-exe на Linux не запускается, а из 302 юнит-тестов там падают 12
платформенных (cmd.exe, разделители путей, разрядность), поэтому `--selftest` и полный набор
тестов возможны только на Windows.

**На собственном Windows-раннере КриптоПро CSP установлен**, на GitHub-hosted его нет. Поэтому
проверка `deps` двусторонняя: шаг сам смотрит регистрацию CryptoAPI-провайдеров в реестре
(обе ветки, exe 32-битный) и ждёт код 0 при найденном CSP и код 2 при отсутствующем.
Просто «ждём код 2» больше не годится. Сверять отчёт по именам провайдеров нельзя —
подробный вывод перечисляет все три известных в любом случае, с пометкой «есть»/«нет»;
маркер берётся из строки про сам CSP, а язык задаётся `--lang ru` явно.

**.NET SDK на Windows-раннере не установлен системно.** Служба идёт под `NT AUTHORITY\NETWORK SERVICE`
и в `Program Files` писать не может, поэтому в `C:\actions-runner-cryptopro\.env` задан
`DOTNET_INSTALL_DIR=C:\actions-runner-cryptopro\_dotnet` — `actions/setup-dotnet` ставит SDK
туда, и каталог переживает перезапуски.

## Подводные камни окружения (реальные, уже наступали)
1. **Манифест WinForms.** Корневой тег строго `<assembly xmlns="urn:schemas-microsoft-com:asm.v1" …>`.
   Лишнее слово (`<assembly manifest …>`) → при запуске «Параллельная конфигурация неправильна» (SxS), сборка при этом проходит. Файл: `src/App/app.manifest`.
2. **Запуск .exe.** Из bash не запускается (`Permission denied`). Используй PowerShell `Start-Process`.
3. **stdout WinExe.** Виден только при redirect в файл; в консоль напрямую ничего не выводит.
4. **Кодировки.** Имена контейнеров (`PP_ENUMCONTAINERS`, `name.key`) — cp1251. Используй `Cp1251`, не `Encoding.Default` (=UTF-8 в .NET).
5. **Хук среды автора.** PowerShell-команда, где рядом стоят `Remove-Item` и путь `C:\Program…`, блокируется целиком. Разноси на отдельные команды.
6. **Тестовые артефакты — персданные.** `extractcert` вытаскивает реальный сертификат (ФИО/СНИЛС/ИНН). Не коммить `.cer/.key/.pfx` (см. `.gitignore`), удаляй после теста.
7. **x86 обязателен, не «для совместимости».** `rtCOMLite.dll` 32-битный и загружается в процесс. В x64 он работал бы только через COM-суррогат (`AppID … DllSurrogate` в реестре), то есть требовал бы установки компонента — ровно то, от чего мы уходим. Не переводи портативную сборку на x64/AnyCPU. Проверено на всех трёх RID: x86 — вшитый rtCOMLite грузится («встроенная копия, без регистрации»); x64 — «не подходит (библиотека x86, процесс x64)» и откат на системный компонент; arm64 — собирается, ограничение то же. CryptoAPI КриптоПро в 32-битном процессе работает: `list` перечисляет контейнеры (провайдеры 75/80/81).
8. **`p12utility` 4.0.8 не умеет `--cptop12`.** В справке есть только `--p12tocp`, `--p12addtocp`, `--cprepair`, `--cppublic` (обратное направление: PKCS#12 → контейнер). Экспорт в `.pfx` сделан через `certmgr` (`CertMgr.cs`).
9. **Консольные утилиты КриптоПро (p12utility, certmgr, csptest) пишут в cp866.** Читать их вывод через `Cp866` — иначе в логе каша. Само приложение с версии 1.2 выводит UTF-8.
10. **«Экспортируемость» проверяется через `KP_PERMISSIONS`** (флаг `CRYPT_EXPORT = 0x4`), а не через `CryptExportKey`: на прямой `CryptExportKey(PRIVATEKEYBLOB)` КриптоПро отвечает `NTE_BAD_KEY_STATE` даже для экспортируемого ключа. Проверено на паре контейнеров: до `--keyexport` `0x00130898`, после — `0x0013089C`, и именно второй успешно выгружается в PFX.
11. **Файловые контейнеры лежат в `%LOCALAPPDATA%\Crypto Pro\<имя>.000`** (считыватель HDIMAGE), имя CSP показывает из `name.key`. Проверено экспериментом на синтетическом контейнере:
    - копия папки **как есть** (папка и `name.key` совпадают с исходными) — CSP её видит;
    - копия с **переписанным** `name.key` — CSP её игнорирует (сверяет имя с содержимым контейнера), причём и после отката имени папка с «чужим» именем так и остаётся невидимой;
    - после `--cprepair` (снятие запрета) переименование проходит — так были получены рабочие `cpxfixed`/`cpxinst`.

    Поэтому `ContainerStore.Install` по умолчанию **не трогает имя**, а если переименование запрошено и CSP копию не принял — полностью переустанавливает контейнер под исходным именем и честно сообщает об этом. Результат всегда проверяется перечислением (`InstallResult.VisibleToCsp`), а не «команда отработала без ошибки».
12. **`csptest -newkeyset` показывает диалог «Аутентификация — КриптоПро CSP»** с запросом нового пароля даже при `-protected=none`. В неинтерактивном прогоне он отваливается с `0x8010006E` (SCARD_W_CANCELLED_BY_USER). Автоматизировать так: найти окно класса `#32770` у процесса и послать ему `WM_COMMAND` с `IDOK` (пустой пароль). Двигать мышкой бесполезно — это не биологический ДСЧ.
13. **Локальный запуск build-версии требует 32-битного рантайма .NET нужной мажорной версии.** Сборка даёт framework-dependent x86; без `Microsoft.WindowsDesktop.App` x86 нужной версии exe падает с `0x80008002`. На машине автора стоит только x86-рантайм 8.0, поэтому после перехода на net10 проверять надо портативную (self-contained) сборку: `pwsh build\publish.ps1`, дальше запускать `publish\CryptoProExport.exe`. На CI по той же причине самопроверка гоняется на портативной сборке.
14. **Размер портативного exe уменьшать больше нечем без потери функциональности.** `PublishTrimmed` SDK запрещает прямо: `NETSDK1175` — обрезка не поддерживается для Windows Forms. `InvariantGlobalization` не даёт ничего (на Windows .NET берёт ICU из системы), `DebugType=none` экономит 25 КБ ценой номеров строк в трассировках. Реальный резерв был один и уже использован: `SatelliteResourceLanguages=ru` убирает сателлиты 12 лишних языков — 8,5 МБ до сжатия, 2,3 МБ в готовом exe.
15. **Отмена длинных операций** доходит до исполнителей через свойство `Cancel` (как `Log`): `ExportPipeline.Cancel` раздаёт токен `RutokenExporter` и `P12Utility`. Прервать вызов внутри COM нельзя — проверки стоят между шагами; запущенная утилита снимается `Kill`. Важно: флаг «убито отменой» ставится **до** `Kill`, потому что `Kill(entireProcessTree: true)` может бросить исключение уже после того, как процесс снят, — иначе отменённый запуск возвращался бы как обычный результат (этот баг поймал тест).
16. **Руководство лежит в `src/Core/guide/<язык>.txt`** (ru + en) и вшивается ресурсами (`GuideText`). Оно же — окно «Справка» и команда `help`. Тесты следят за наличием разделов, упоминанием всех команд и шириной строк ≤78 символов (руководство печатается в консоль как есть), причём **для обоих языков**. Добавил команду — допиши её в оба файла, иначе тест упадёт.
17. **Локализация: 20 языков, по файлу на язык** — `src/Core/i18n/<код>.txt`, формат `ключ = значение`, вшиваются `EmbeddedResource` с явным `LogicalName`. Добавить язык = положить файл и перечислить код в `LocalizationTests.Expected`. Правила, которые уже стоили времени:
    - **`WithCulture=false` в csproj обязателен.** Без него MSBuild принимает имена `ru.txt`, `zh-Hans.txt` за ресурсы сателлитных сборок и выносит их из основной сборки — ресурс просто исчезает.

21. **PKCS#11 на Рутокен Lite не видит контейнеров КриптоПро — путь закрыт.** Проверено на живом
    токене пробником на `Pkcs11Interop` 5.3.0 поверх системной `C:\Windows\System32\rtPKCS11ECP.dll`
    (Cryptoki 2.40, «Rutoken ECP PKCS #11 library» 2.18). Слот и токен видны штатно
    (`Aktiv Rutoken lite 0`, модель `Rutoken lite`, прошивка 9.02), `C_Login(CKU_USER)` проходит,
    но `C_FindObjects` с пустым шаблоном возвращает **ноль объектов** — и до авторизации, и после.
    Значит контейнеры КриптоПро на Lite вообще не PKCS#11-объекты, и искать `CKO_DATA` с меткой
    контейнера бессмысленно. **Уточнение от 13.08.2026 (п. 28): «ноль объектов» — про контейнеры CSP,
    а не про носитель. Само хранилище объектов PKCS#11 у Lite рабочее и принимает записи.** На том же токене в тот же момент `csptest -keyset -enum_cont -fqcn`
    показывает 3 контейнера на `\\.\Aktiv Rutoken lite 0\…` — то есть дело не в токене и не в PIN.
    Заодно проверено штатное копирование контейнера средствами CSP:
    `csptest -keycopy -contsrc "\\.\Aktiv Rutoken lite 0\<имя>" -contdest "\\.\HDIMAGE\<имя>" -pinsrc … -silent`
    падает на `CopyPrivateKey(AT_KEYEXCHANGE)` с `0x8009000b` (`NTE_BAD_KEY_STATE`) — тот самый
    запрет на экспорт. Снять его нечем: `p12utility --cprepair` принимает `--container_folder`,
    то есть папку с шестью `*.key`, а взять её неоткуда. Круг замкнут.
    Чем читает сам CSP: в его составе есть `rutoken.dll`, экспортирующий
    `rutokenecpsc_media_get_table` / `rutokenecpmsc_media_get_table` / `rutokennfc_media_get_table`.
    Это плагин-«носитель» поверх собственного PC/SC-стека КриптоПро (`cpscard.dll`, `pcsc.dll`),
    а не обёртка над rtPKCS11ECP: из внешних библиотек `rutoken.dll` тянет только
    ADVAPI32/KERNEL32/USER32/msvcrt/ntdll. Отсюда и объяснение п. 20: rtCOMLite — API файловой
    памяти Рутокен S, а Lite обслуживается по смарт-карточному профилю, где та же файловая память
    через старый API не видна. Следующий шаг для Lite — только APDU-уровень.
    **PIN трогать осторожно.** У Рутокена счётчик попыток; проверять дефолтность PIN надо *до*
    авторизации. В PKCS#11 для этого есть штатный флаг `CKF_USER_PIN_TO_BE_CHANGED` в
    `CK_TOKEN_INFO` (в Pkcs11Interop — `TokenInfo.TokenFlags.UserPinToBeChanged`): он и означает
    «PIN дефолтный», то есть равнозначен `IsPINDefault` из rtCOMLite и не требует ни одной попытки
    входа. Рядом лежат `UserPinCountLow`, `UserPinFinalTry`, `UserPinLocked` — по ним видно, что
    счётчик в норме. Пробник авторизуется только если дефолтность подтверждена и счётчик чист.

22. **Рутокен ЭЦП (Rutoken ECP, ATR `Rutoken DS`) — PKCS#11 отдаёт контейнер и сертификат без PIN.**
    Проверено на живом `Aktiv Rutoken ECP 0` (модель `Rutoken ECP`, прошивка 23.02) с системной
    `rtPKCS11ECP.dll` 2.18. В отличие от Lite (п. 21, там `C_FindObjects` пуст), на ЭЦП PKCS#11
    показывает объекты, и главное — **публичные, читаются до `C_Login`**:
    - `CKO_DATA` с `CKA_APPLICATION = "CryptoPro CSP"` (у нашего 3525 байт) — **разобран 12.08.2026,
      см. п. 25: это цепочка сертификатов УЦ и метаданные, а не «слепок контейнера».**
    - `CKO_CERTIFICATE` с меткой контейнера — сам сертификат в DER (2426 байт), **читается без CSP и
      без PIN**. Отсюда рабочая CSP-free ветка: `Pkcs11Token` извлекает `.cer` прямо с токена.
    - `CKO_PRIVATE_KEY` виден только после `C_Login`, `CKA_EXTRACTABLE=false`, `CKA_SENSITIVE=true` —
      закрытый ключ через PKCS#11 не выгружается (аппаратно), как и ожидалось.

    rtCOMLite на ЭЦП ведёт себя как на Lite: обход находит 20 папок и 0 файлов. Поэтому
    `RutokenExporter` (файловый путь) для ЭЦП/Lite бесполезен, а `list`/`deps`/`token` идут через
    `Pkcs11Token`. Класс мягко деградирует: нет `rtPKCS11ECP.dll` (нет драйвера) или нет токена —
    `Enumerate` возвращает пустой список, ничего не роняя (тест `Enumerate_NeverThrows`).
    Отмена доходит и сюда: `Enumerate` принимает `CancellationToken` и проверяет его между слотами
    и объектами (внутри вызова драйвера прервать нельзя — как в п. 15). Без этого зависший стек
    PC/SC держал бы окно, потому что кнопка «Отмена» есть у всех длинных операций.
    Имя файла для снятого с токена `.cer` собирает `Pkcs11Token.CertFileName`/`UniqueCertPath`:
    метка контейнера **плюс серийный номер токена**, при совпадении — числовой суффикс. Метки на
    разных токенах совпадают сплошь и рядом, и без серийника один `.cer` затирал бы другой.

23. **Снять контейнер с Рутокен ЭЦП средствами CSP можно только если ОБА ключа экспортируемые.**
    Проверено `csptest -keycopy` на синтетическом контейнере (не на боевом):

    - создать контейнер прямо на токене (`-newkeyset`) — аппаратный ДСЧ токена, но упирается в

    игнорирует. `p12utility --cprepair` по-прежнему требует папку с шестью `*.key`, а взять её с

24. **Аудит без железа (v1.4.2) — четыре класса дефектов, которые здесь легко посеять снова.**
    Ни один из них не проявляется на «счастливом пути» и ни один не ловился прежними тестами.
    - **Свойства контролов из рабочего потока.** Действия GUI идут в `Task.Run`, а `_txtDest.Text`,
      `_txtPin.Text`, `_txtP12.Text` читались напрямую. Класс сам придерживается правила «UI только
      через `Invoke`» (`SelectedContainerName`, `AddRow`, диалоги) — здесь оно было нарушено, и при
      закрытии окна во время операции обращение бросает `ObjectDisposedException`. Читай поля только
      через `MainForm.TextOf`.
    - **Кавычка внутри значения аргумента.** Утилиты КриптоПро получают командную строку целиком и
      разбирают её сами, поэтому пароль `my"pass` доезжал до `certmgr` как `my`, и `.pfx` молча
      получал не тот пароль, который ввёл пользователь. `P12Utility.Quote` теперь отвергает кавычку
      явной ошибкой (`err.arg.quote`); сообщение намеренно **не содержит самого значения** — иначе
      пароль попал бы в журнал через `catch` в `MainForm.Run`.
    - **Маскирование пароля искало флаг простым `IndexOf`.** Имя `.pfx` выбирает пользователь, и файл
      вроде `backup -pin .pfx` уводил маску на путь, а настоящий пароль писался в журнал открытым
      текстом. `IndexOfFlag` считает только текст вне кавычек.
    - **Имя контейнера с токена — это данные, а не имя папки.** `Path.GetInvalidFileNameChars()` не
      считает точку недопустимой, поэтому имя `..` из `name.key` проходило фильтр и
      `Path.Combine(parentDir, "..")` писал шесть `*.key` в родительский каталог. Чисти имя через
      `RutokenContainer.SafeFolderName`.

    Заодно поправлено поведение **без токена** (основной режим на машине без железа): `list` печатает
    секцию PKCS#11 всегда, даже пустую (молчание читалось как «не смотрели»), а `export`/`full`
    возвращают **2**, если не снято ни одного контейнера — прежний код 0 скрипт принимал за успех.
    В `list` пробрасывается лог PKCS#11: без него сбой драйвера выглядел как «токенов нет».
    `RutokenExporter.ReadAllContainers` держит `Acquire()` и `BeginTransaction()` внутри `try`:
    иначе занятый другим процессом токен (`SCARD_E_SHARING_VIOLATION`) оставлял считыватель
    захваченным, и остальные токены уже не обходились.

25. **Блоб `CKO_DATA` разобран: в нём НЕТ ключевого материала. Главная надежда ROADMAP закрыта.**
    Снят с живого токена 12.08.2026 (3525 байт, `sha256=4b17528a5ef9…`) и разобран оффлайн.
    Раскладка целиком:

    | Смещение | Что |
    |----------|-----|
    | 0…20 | заголовок: `01 00 00 00 01 00 00 00`, нули, `2C 00 00 00` |
    | 21…72 | длина 19 + ASN.1 `30 11 81 0F` с `20290225082301Z`, затем ASCII-строка OID `1.2.643.2.2.37.3.10` |
    | 73…2109 | `SET { SEQUENCE { сертификат } }` — **УЦ ФНС** (2032 байта DER, до 23.01.2039) |
    | 2137…3506 | `SET { SEQUENCE { сертификат } }` — **корневой Минцифры** (1365 байт, до 08.01.2040) |
    | 3507…3524 | ASCII-строка OID `1.2.643.2.2.37.3.3` |

    **Чего внутри нет** (проверено поиском по байтам, а не на глаз):
    - сертификата владельца — байты `CKO_CERTIFICATE` (2426) в блобе не встречаются;
    - открытого ключа — 64 байта из `CKO_PUBLIC_KEY` не встречаются;
    - **ни одного `04 20`, то есть ни одного 32-байтового `OCTET STRING`.** Закрытый ключ
      ГОСТ-256 и маска — ровно 32 байта каждый, значит ключевого материала нет в принципе;
    - сигнатур файлового формата (`30 44 04 20`, `30 36 04 20`).

    Отсюда вывод, закрывающий целое направление: **разбирать `CKO_DATA` в шесть `*.key`
    бессмысленно — собирать не из чего.** Прежняя формулировка «сериализованный контейнер
    целиком» (п. 22 в редакции v1.4.0) оказалась неверной: это метаданные плюс цепочка доверия,
    которую CSP держит рядом с ключом. Бэкап боевого ключа с Рутокен ЭЦП невозможен ни одним
    из известных путей.

    **Заодно проверено на живом токене** (и это последний открытый вопрос по железу):
    - `csptest -keycopy` токен→HDIMAGE на боевом контейнере — `0x8009000b NTE_BAD_KEY_STATE`,
      как и предсказывал п. 23;
    - обратное копирование HDIMAGE→токен прошло успешно (контейнер `cpxref`, код 0), CSP его
      увидел сразу, **а PKCS#11 не показал** — ни нового `CKO_DATA`, ни других объектов.
      То есть контейнеры, которые кладёт на ЭЦП сам CSP, PKCS#11-объектами не становятся,
      и «эталонная пара блоб ↔ шесть `*.key`» так не получается. Проверять это после
      физического переподключения уже незачем: даже появившийся блоб содержал бы цепочку
      сертификатов, а не ключ. Тестовый контейнер с токена удалён, боевой не тронут.

    **Как перепроверить за минуту, не доверяя этому тексту.** Полный дамп токена
    (`CK_TOKEN_INFO`, 45 механизмов, все объекты с `CKA_VALUE`) лежит локально в
    `token-session\session\01-baseline\slot1\`. Сам блоб — `public\04_CKO_DATA_*.bin`,
    3525 байт, `sha256 = 4b17528a5ef90326be243076a1100fade2ab3a7fc51278d2e06e25f0545c0c21`.
    Ключевая проверка — счётчик 32-байтовых `OCTET STRING`, он должен дать ноль:

    ```powershell
    # Имя файла содержит метку контейнера, поэтому путь сначала разрешаем: статический
    # [IO.File]::ReadAllBytes маску не раскрывает и упал бы с FileNotFoundException.
    $f = Get-ChildItem 'token-session\session\01-baseline\slot1\public\04_CKO_DATA_*.bin'
    $b = [IO.File]::ReadAllBytes($f.FullName)
    $n = 0; for ($i = 0; $i -lt $b.Length - 1; $i++) { if ($b[$i] -eq 0x04 -and $b[$i+1] -eq 0x20) { $n++ } }
    $n   # ноль = 32-байтовых OCTET STRING нет, то есть нет и ключевого материала
    ```

    Второй способ, наглядный: вырезать байты 77…2108 и 2141…3505 и открыть как `.cer` —
    получатся ровно сертификаты УЦ ФНС и Минцифры (они же выложены отдельными файлами
    в резервной копии на рабочем столе владельца).

    Позднее, 26.08.2026, отдельные Рутокен S и JaCarta LT закрыли пассивные APDU-сценарии

26. **Матрица «модель → снимается ли закрытый ключ» — в README. Формулировки строго по
    уровню доказанного, три градации, не смешивать:**
    - **Рутокен S** — файловая память; с 26.08.2026 production-путь — `RutokenSApdu`, а не
      `rtCOMLite`. Проверено на `VID_0A89/PID_0020`: 6 `*.key`, обе пары `…98 → …9C`,
      HDIMAGE и PFX. Пиши твёрдо «снимается».
    - **Рутокен ЭЦП** — ключ в чипе, `CKA_EXTRACTABLE=false` — это **аппаратный** флаг носителя.
      Здесь «нет» сказано твёрдо: проверено на живом ЭЦП 12.08.2026 **тремя независимыми путями**,
      а не только флагом — файловый обход `rtCOMLite` 19 папок / 0 файлов; `certmgr -export -pfx`
      (CryptoAPI, в обход `CKA_EXTRACTABLE`) → `0x8009000b`, PFX не создан; `csptest -keycopy`
      токен→диск → `0x8009000b`.
    - **Рутокен Lite** — снимается по APDU; путь реализован в `RutokenLiteApdu`, ключ
      восстановлен и проверен `d·G==Q`, полный двухключевой E2E закрыт.
    - **JaCarta LT** — отдельный Datastore APDU (`JaCartaLtApdu`), не PRO и не Lite.
      Проверено 26.08.2026 на `VID_24DC/PID_0102`: 6 файлов, обе пары экспортируемы,

    - **Рутокен ЭЦП 3.0** — отдельная строка, не сводимая к 2.0. **Проверено прямым опытом

      их не удалось ни одним из четырёх применимых путей, а неизвлекаемость чипа подтверждена
      отдельным опытом на своей PKCS#11-паре. Теперь «нет» можно писать твёрдо, а не только через
      `CKA_EXTRACTABLE`. Плюс носитель — ФКН, ключ с диска на него ещё и не записать (п. 27).

    Смысл проекта — игнорировать `CKA_EXTRACTABLE` через файловый путь — на ЭЦП физически
    неприменим: игнорировать флаг можно, но файловая память пуста, читать нечего. На сам ЭЦП
    сеанс тратить незачем — путей нет; на Lite остаётся только APDU-реверс. Полная таблица и
    что на этих носителях всё же доступно (сертификат — только на ЭЦП; диагностика) — в
    `README.md`, раздел «На каких носителях снимается закрытый ключ».

27. **Рутокен ЭЦП 3.0 (прошивка 30.02) — сеанс 13.08.2026. Отличается от 2.0 сильнее, чем кажется.**
    Строка модели PKCS#11 у 2.0 и 3.0 **одинаковая** (`Rutoken ECP`), ATR тоже (`Rutoken DS`), поэтому
    различать их надо по прошивке и механизмам: у 3.0 `fw=30.02`, аппаратная 60.01, **69 механизмов,
    включая RSA 512–4096 и ECDSA**; у 2.0 — `fw=23.02` и 45 механизмов без RSA/ECDSA.
    - **КриптоПро CSP 5.0 R2 (5.0.13800) держит 3.0 как ФКН.** В диалоге создания контейнера носитель
      называется `rutoken_fkc_<серийник>` и запрашивается **новый пароль ФКН**. Отсюда главное:
      `csptest -keycopy` с диска **на** 3.0 падает на `CopyPrivateKey(AT_KEYEXCHANGE)` с
      `0x80090029 NTE_NOT_SUPPORTED`, тогда как тот же контейнер копируется и в HDIMAGE, и на Lite
      (обе проверки в тот же момент, код 0). То есть на 3.0 ключ полагается **генерировать на
      носителе**, импорт готового не поддерживается.
    - **Различай две разные операции — иначе выводы противоречат друг другу.** Не работает именно
      **импорт готового контейнера с диска** (`keycopy` HDIMAGE→3.0, `0x80090029`), и рецепт из
      п. 23 «HDIMAGE→токен работает всегда» для 3.0 в этой части неверен. А вот **создание
      контейнера прямо на носителе** (`csptest -newkeyset` через диалог ФКН) работает: позже, уже
      с согласия владельца, пароль ФКН и PUK были заданы и полноценный тестовый контейнер на 3.0
      создан — см. п. 36. Первоначальная оговорка «пароль ФКН не задавали, это меняет состояние
      чужого токена» относилась к тому моменту, а не к возможностям носителя.
    - Тестовые объекты PKCS#11 при этом кладутся независимо от CSP, см. `token-session\visprobe\`.

28. **Политика видимости PKCS#11 подтверждена прямым опытом — и на ЭЦП 3.0, и на Lite.**
    Прежний вывод «сертификат читается без PIN» (п. 22) снят с прошивки 23.02 и с боевого контейнера,
    поэтому его перепроверили независимо от контейнеров: пробник `token-session\visprobe\` кладёт на
    токен четыре объекта — `CKO_DATA` и `CKO_CERTIFICATE`, каждый в вариантах `CKA_PRIVATE=false/true`,
    — затем открывает **новую сессию без `C_Login`** и смотрит, что видно. Результат одинаков на обоих:
    **публичные видны и их `CKA_VALUE` читается без входа, приватные не видны вовсе**; после `C_Login`
    видны все четыре. Значит тезис справедлив и для 30.02, а зависит он не от модели и прошивки, а от
    того, каким УЦ выставил `CKA_PRIVATE`. Объекты после опыта удалены, на токенах снова 0.
    **Заодно опровергнута формулировка «на Lite объектов PKCS#11 нет вовсе, брать нечего»** (п. 21,
    README): хранилище объектов у Lite **рабочее** — оно приняло и `CKO_DATA`, и `CKO_CERTIFICATE`.
    Ноль объектов у виденных Lite — свойство конкретных экземпляров, а не носителя, и сертификат,
    выданный УЦ через PKCS#11, утилита сняла бы и с Lite. Экземпляров Lite за сеанс было два
    (прошивки 9.02 и 8.0), оба пусты по PKCS#11, при этом на первом CSP видит три своих контейнера.
    Заодно проверено, что утилита корректно отрабатывает **три токена сразу** и разрывы в нумерации
    слотов (0, 2, 3): `deps` перечисляет все три, код 0.

29. **`rtISCard::ReadBinary` рушит кучу процесса на ЭЦП 3.0 — второй ядовитый вызов после п. 19.**
    `list` (и любой путь через `RutokenExporter`) умирал с `0xC0000374` при вставленном ЭЦП 3.0,
    воспроизводимо, без единой строки в журнале после «PIN по умолчанию». Локализовано пошаговым
    пробником `token-session\rtprobe\` (x86, журнал сбрасывается на диск перед каждым вызовом):
    обход доходит до `/4096/4097/`, где лежит один файл 256 байт, и умирает **внутри**
    `rt.ReadBinary(32768, 0, 256)`. Порча в нативном коде — `catch` бесполезен, как и в п. 19.
    На прежних ЭЦП 2.0 и Lite файлов было **ноль**, поэтому `ReadBinary` там не вызывался ни разу и
    баг не проявлялся: он ждал первого носителя с непустым каталогом.
    Лечение — не обходить смарт-карточные Рутокены вовсе (`RutokenExporter.ShouldWalk`): контейнеров
    в их файловой памяти всё равно нет (пп. 20, 22), а список пропускаемых считывателей даёт
    `Pkcs11Token.SmartCardReaders`; при отсутствии драйвера PKCS#11 работает запасной признак — имя
    считывателя (`Aktiv Rutoken ECP 0`, `Aktiv Rutoken lite 0`). Побочная польза: PIN чужого токена
    больше не трогается вообще.

30. **Сертификат без парного `CKO_DATA` терялся.** `Pkcs11Token` привязывал сертификат к контейнеру по

31. **`csptest -enum_cont` молча пропускает считыватели.** Если карта или считыватель в этот момент
    недоступны (соседний процесс держал сессию PC/SC, только что был холодный сброс), команда
    печатает **только HDIMAGE**, завершается с кодом 0 и словом `OK` — ни ошибки, ни предупреждения.
    Выглядит это ровно как «контейнеры на токене пропали», и один раз стоило получаса паники.
    Признак подмены: прогон занимает ~0,1 с вместо ~1,5–2 с (обращения к картам нет). Проверять надо
    не повтором той же команды, а обращением к контейнеру **по имени** (`-check` проходит и тогда,
    когда перечисление пусто) и свободной памятью токена в дампе PKCS#11. Холодный сброс карт без
    физического переподключения — `pwsh token-session\reset-cards.ps1` (PC/SC `SCARD_UNPOWER_CARD`);
    после него дать картам секунду, иначе первый же `enum_cont` снова окажется «пустым».

32. **Одна библиотека PKCS#11 = один вендор. JaCarta утилита не видела вовсе — исправлено (v1.4.3).**
    Сеанс 13.08.2026, четыре считывателя сразу. `rtPKCS11ECP.dll` отдала **три** слота (все Рутокены)
    и не увидела JaCarta; `jcPKCS11-2.dll` — ровно **один** слот (только JaCarta). Это не настройка,
    а устройство PKCS#11: библиотека вендора обслуживает свои носители. Поэтому
    `Pkcs11Token.LibraryCandidates()`, искавший только `rtPKCS11ECP.dll`, делал JaCarta невидимой для
    `deps`/`list`/`token` целиком, хотя её контейнер КриптоПро при этом прекрасно виден CSP.
    Лечение: `KnownLibraries` (вендор → dll), `AvailableLibraries()` возвращает по одной найденной
    библиотеке на вендора, `Enumerate` грузит их по очереди и объединяет слоты, дедуплицируя по имени
    считывателя. Сбой одной библиотеки не скрывает носители остальных, отсутствие любой — не ошибка.
    - **Модель JaCarta в PKCS#11 — просто `PRO`.** `Classify` по одной строке модели давал «не
      опознан», поэтому у него появился второй аргумент — производитель (`Aladdin R.D.`).
      Обратное направление намеренно не сделано: `Aktiv Co.` с невнятной моделью так и остаётся
      `Unknown`, иначе носитель попал бы в файловый обход rtCOMLite как Рутокен S.
    - **`jcPKCS11-2.dll` лежит только в системном каталоге** (`System32` + `SysWOW64`, 27.08.2024,
      x86 5 976 744 байт). В `C:\Program Files\JaCarta Unified Client` библиотеки нет — кандидаты в
      Program Files перечисляются только для Рутокена.
    - **rtCOMLite JaCarta не показывает**: при четырёх считывателях `EnumReaders` вернул три, только
      Рутокены. Падения из п. 29 тут не было и быть не могло, но чужие носители теперь исключаются
      из файлового обхода **в двух местах сразу** — файловая память rtCOMLite это API Рутокен S,
      к чужой смарт-карте она неприменима, а цена ошибки (порча кучи внутри нативного вызова)
      слишком велика:
      `Pkcs11Token.SmartCardReaders` кладёт в `SkipReaders` и `RutokenKind.Other` (основной путь —
      знание PKCS#11 о производителе), а `RutokenExporter.ShouldWalk` отсеивает `Other` ещё и по
      имени считывателя (запасной путь, когда драйвера PKCS#11 в системе нет). Одного второго мало:
      имя считывателя бывает безликим (`ACS ACR38U 0`), и классификация по нему даёт `Unknown` —
      это замечание Codex на PR #25.

35. **JaCarta с PIN проверена полностью: штатными способами ключ не снять, но по APDU — снимается (см. итог ниже).**
    Сеанс 13.08.2026, PIN получен от владельца (лежит в `secrets.txt`, в репозиторий не попадает).
    Опыт поставлен на **своём тестовом контейнере**, сгенерированном прямо на носителе, — чужие
    контейнеры для этого не годятся, и вот почему.

    **Сначала ловушка, в которую легко попасть.** Первый же `csptest -keycopy` с JaCarta на диск
    прошёл с кодом 0 и дал шесть `*.key` — но это ничего не доказывало: у ключа в том контейнере
    флаг `CRYPT_EXPORT` **уже был взведён** (`checkexport` на копии → `KP_PERMISSIONS = 0x0013089C`).
    Контроль на `Aktiv Rutoken lite 1` дал ровно то же — код 0 и тот же `0x0013089C`. То есть
    **экспортируемый ключ CSP штатно копирует с любого носителя**, и вендор тут ни при чём. Всякий
    вывод про «снимается / не снимается» имеет смысл только на контейнере с **неснятым** запретом.

    **Как получен годный образец.** `token-session\make-token-container.ps1` создал контейнер прямо
    на JaCarta (`-newkeyset`, ключ генерируется на носителе). Это, кстати, поправка к пессимизму
    п. 23: скрипт закрывает оба модальных окна («Выбор ключевого носителя» и «Био ДСЧ»), так что
    автоматизировать создание всё-таки можно. Без него `-silent` отваливается с `0x80090022`
    (`NTE_SILENT_CONTEXT` — «нужен диалог, а контекст тихий»). Свежий контейнер оказался ровно тем,
    что нужно: `checkexport` → **обмен `0x00130898`, подпись `0x00122898`, флага `CRYPT_EXPORT` нет**.

    **Три независимых пути, все закрыты:**
    - `csptest -keycopy` токен→HDIMAGE → **`0x8009000B NTE_BAD_KEY_STATE`**;
    - `certmgr -export -pfx` (CryptoAPI, идёт мимо PKCS#11 и его флагов) → **`0x8009000B`**,
      файл `.pfx` не создан. Сертификат для этого клался в контейнер `csptest -makecert` и
      ставился в «Личное» `certmgr -inst`;
    - PKCS#11 с верным PIN → **0 объектов и до `C_Login`, и после**, причём даже для только что
      созданного CSP-контейнера. Это то же, что на Рутокен ЭЦП (п. 25): контейнеры CSP объектами
      PKCS#11 не становятся. Плюс rtCOMLite считыватель JaCarta вообще не показывает (п. 32).

    **Итог (уточнён 13.08.2026): JaCarta PRO — закрытый ключ снимается через APDU.** Штатные пути
    (`csptest -keycopy`, `certmgr`, PKCS#11) дают `0x8009000b` — но это политика CSP, не карта.
    APDU-разбор показал, что носитель **пассивный** (подпись на хосте, `primary.key`+`masks.key`
    уходят с карты и для неэкспортируемого ключа), а закрытый ключ восстановлен офлайн и сверен с
    открытым (`d·G==Q`). У неэкспортируемого `primary.key = SEQUENCE { OCTET STRING, [0] }`, ключ —
    в поле `[0]`; `d = decrypt(CPKDF(""), [0]) · маска⁻¹ mod q`. Метод (нативный winscard-прокси и
    frida), разбор поля `[0]` и проверка — в `docs/apdu/jacarta-pro.md`, инструменты в
    `docs/apdu/harness/`. Параллель с Рутокен Lite (тоже пассивный, ключ снят по APDU) прямая.

    **Уборка.** Тестовый контейнер и его сертификат удалены, копии на HDIMAGE удалены,
    состояние сверено `enum_cont` до и после. Отдельная памятка: **перед уборкой сверяй список не
    только со своим журналом, но и с владельцем.** Контейнер `… - Copy - Copy`, появившийся на
    JaCarta посреди сеанса, я принял за собственный побочный эффект и удалил — на деле его создал

36. **Рутокен ЭЦП 3.0 — «неизвлекаемость» проверена ПРЯМЫМ опытом, а не только флагом (13.08.2026).**
    Прежняя оговорка «живой экземпляр был пуст, извлечение не пробовали» закрыта: на токене создан
    настоящий боевой-подобный контейнер и прогнаны все пути снятия. Итог —
    ключ не снимается ни одним, и теперь это сказано твёрдо, а не выведено из `CKA_EXTRACTABLE`.
    - **Как создан контейнер.** `csptest -newkeyset` прямо на токене через диалог ФКН

      пароль ФКН** и **ФКН PUK**, оба заданы `12345678` (= заводской PIN). Пустой пароль отвергается

    - **Четыре пути снятия — применительно к ключам самого контейнера, все отказали:**
      1. `rtCOMLite` — файлов контейнера этим путём не обнаружено. Формулировать это как «обход дал
         0 файлов» **нельзя**: рабочий `RutokenExporter` смарт-карточный Рутокен вообще не обходит
         (`ShouldWalk`, п. 29), так что обхода как эксперимента здесь не было. Прямой пробник
         `rtprobe` на этом же токене находил ровно один файл 256 байт в `/4096/4097/` и умирал
         внутри `ReadBinary` — это служебный объект носителя, а не `*.key` контейнера;
      2. `csptest -keycopy` токен→HDIMAGE → `0x8009000b NTE_BAD_KEY_STATE` (тот же код, что на боевом ФНС);
      3. `certmgr -export -pfx` из установленного в хранилище сертификата → `0x8009000b`, PFX не создан
         (в выводе видно `Контейнер: SCARD\rutoken_fkc_48e243b5\cpxfull` — CSP держит его как ФКН);
      4. команда утилиты `export` → код 2, «снято контейнеров: 0», смарт-карточный Рутокен пропущен.

      ключам `cpxfull` PKCS#11 неприменим в принципе: созданный CSP контейнер объектом PKCS#11 не
      становится (см. ниже), читать через него там нечего. Поэтому неизвлекаемость проверялась на
      **отдельной своей** PKCS#11-паре, сгенерированной на том же токене: `CKA_EXTRACTABLE=false`
      → `CKA_NEVER_EXTRACTABLE=true`, чтение `CKA_VALUE` закрытого ключа →
      `CKA_VALUE could not be read`, `C_WrapKey` → `CKR_KEY_NOT_WRAPPABLE`
      (`token-session\visprobe\ --genkey`). Это свойство носителя, а не прямое измерение на тех
      двух ключах — складывать оба опыта в «пять путей на одном контейнере» нельзя.
    - **Контейнер, созданный CSP, объектом PKCS#11 не стал** (подтверждает п. 25 ещё раз): в дампе
      видны только положенные пробником `cpxvis-*` и ГОСТ-ключ, а `cpxfull` — нет. Значит и сертификат
      из такого контейнера командой `token` не снять: он не публичный PKCS#11-объект, а лежит внутри
      контейнера CSP.
    - **Удаление ФКН-контейнера.** `-deletekeyset -silent` не проходит (`0x80090022 NTE_SILENT_CONTEXT`

      через CryptoAPI: `CryptAcquireContext(cont, prov80, CRYPT_DELETEKEYSET)` вернул TRUE и удалил

37. **Рутокен Lite: контейнер КриптоПро читается по APDU мимо CSP — путь вскрыт (13.08.2026).**
    Последний неисследованный путь из п. 21 («свой PC/SC-стек CSP на уровне APDU») пройден. `rutoken.dll`
    сам WinSCard не импортирует, но его импортирует `pcsc.dll` CSP, поэтому вся APDU-переписка Lite идёт
    через штатный `winscard.dll` Windows и перехватывается **прокси-`winscard.dll`** рядом с `csptest.exe`
    (каталог CSP защищён — копируется целиком, контроль целостности КриптоПро сверяет хеш файлов, не путь;
    прокси экспортирует все 80 символов реального winscard, форвардя 77 функций на переименованную копию
    `realscard.dll` и перехватывая `SCardTransmit`/`SCardConnect*` — неполный экспорт даёт `0xC0000139`).
    - **Раскладка.** Контейнер = DF `<idx>00`, шесть `*.key` = EF `<idx>0N`. По содержимому: EF `xx06`
      `name.key`; `xx03` header+сертификат (внутри OID кривой `1.2.643.2.2.36.0`); `xx02`/`xx05`
      `primary`/`primary2` = `SEQ{OS32}` (маскированные закрытые ключи обмена/подписи); `xx01`/`xx04`
      `masks`/`masks2` = `SEQ{OS32,OS12,OS4}` (маска+соль+CRC). Команды: `SELECT` по пути
      `00 A4 08 04 Lc 1000 1003 <DF> [<EF>] 00`, `READ BINARY 00 B0`, `VERIFY PIN 00 20 00 02 08 <pin>`,
      FCP тег `80` = размер. `csptest -keycopy` читает `primary`/`masks` (`READ BINARY`), делает ротацию
      маски (`UPDATE BINARY`) и лишь **потом** падает на `0x8009000b` в `CopyPrivateKey` — то есть запрет
      софтверный, ключевой материал уже снят.
    - **Собственный съём.** Утилита `litedump` (прямой `SCardTransmit`, только чтение) прочитала все шесть
      `*.key` **без КриптоПро** — это готовый CSP-free путь для Lite, аналог `RutokenExporter` для S.
    - **Снятие маски доведено и проверено байтово.** Из прочитанных `primary.key`+`masks.key`
      офлайн-разбором §3.1 вычислен закрытый ключ `d`, и `d·G == Q` **совпало** с открытым ключом из
      сертификата. Сработавшие параметры (единственное совпадение в переборе): пароль контейнера **пуст**
      (CPKDF в 2 итерации, как у файловых; PIN в KDF не участвует), Стрибог-256 в нативном порядке
      BouncyCastle, S-box Param-Z строки `k1..k8`, `primary` расшифрован ГОСТ 28147-ECB, маска сырая, оба
      числа LE, `d=primary·mask⁻¹ mod q`, кривая CryptoPro-A. Проверка — на **BouncyCastle**
      (`Gost3411_2012_256Digest`+`Gost28147Engine`+`GostR3410-2001-CryptoPro-A`). Прежняя неудача с
      `gostcrypto` объяснилась: у Magma 34.12 иная байтовая конвенция, чем у ГОСТ 28147-89. Значение `d`
      (реальный ключ владельца) в репозиторий и память не выносится. Осталась инженерная часть — перенос
      пути в `Core` (`RutokenLiteApdu`→§3.1→PKCS#8/PFX, ROADMAP P1). Подробности, протокол и
      воспроизведение — [docs/apdu/rutoken-lite-fw9.md](docs/apdu/rutoken-lite-fw9.md). Оснастка (прокси,
      `litedump`, C#-пробник `recon/`, логи с персданными) — локально в scratchpad, в репозиторий не идёт.
38. **Сертификат в `header.key` лежит открытым DER — прежнее «его там нет» было ошибкой измерения
    (13.08.2026).** Он записан в элементе с **неявным контекстным тегом**: `[5]` — сертификат
    первого ключа контейнера (`primary.key`), `[6]` — второго (`primary2.key`); рядом `[10]` и
    `[11]` — восьмибайтовые отпечатки тех же ключей. Сканирование «ищем `30 82` и разбираем как
    X.509» его пропускает, потому что снаружи стоит байт тега `0x85`/`0x86`, а не `0x30`.
    BouncyCastle отдаёт такой элемент как `OCTET STRING`, поэтому обход по ASN.1 находит его сам —
    достаточно попробовать разобрать содержимое как сертификат (`ContainerKeyExtractor.Walk`).
    Проверено на всех трёх реальных контейнерах владельца и на синтетическом `cpxtest`: openssl
    читает вынутый DER как валидный X.509, а первые 8 байт X открытого ключа совпадают с `[10]`.
    Отсюда же правило выбора: в контейнере с двумя ключами сертификата два, и брать надо тот,
    чей открытый ключ равен посчитанному `d·G`, — это заодно второй оракул правильности разбора.
    Пригодится и для APDU-пути с Lite (п. 37): EF `xx03` — тот же `header.key`, и сертификат
    оттуда достаётся тем же `ContainerKeyExtractor`, без отдельного разбора.
39. **PKCS#12, собранный по стандарту, КриптоПро не импортирует — и дело не в нашем конверте.**
    Свой `.pfx` (сертификат открытым `certBag`, ключ в `pkcs8ShroudedKeyBag` под
    `pbeWithSHAAnd3-KeyTripleDES-CBC`, имитовставка HMAC-SHA-1) читается OpenSSL и BouncyCastle,
    но `certmgr -install -pfx` отвечает `0x800704c7 ERROR_CANCELLED`. Что проверено:
    - **конверт наш — рабочий**: мешки из `.pfx`, сделанного самим `certmgr`, пересобраны нашей
      обвязкой (наш `AuthenticatedSafe`, наш DER, наша имитовставка) — импорт прошёл с кодом 0;
    - **дело не в форме PKCS#8**: отвергнуты все шесть сочетаний
      `OCTET STRING` little-endian / big-endian / `INTEGER` × зашифрованный и открытый мешок;
    - **дело не в маршрутизации к провайдеру**: без атрибута `1.3.6.1.4.1.311.17.1` (имя CSP)
      Windows-импорт (`certutil -importpfx`) отвечает `NTE_BAD_KEYSET` — уходит к Microsoft CSP,
      а с атрибутом — тот же `ERROR_CANCELLED`, то есть до КриптоПро дошло и оно отказалось;
    - `p12utility --p12tocp` наш файл тоже не открывает («Ошибка при открытии ключевого
      контейнера PKCS#12»).
    Свой `.pfx` КриптоПро защищает **своим** PBE `1.2.840.113549.1.12.1.80` (соль 16 байт,
    итераций 2000, шифртекст 172 байта для ключа 256 бит). Первый перебор гипотез по нему
    (CPKDF из контейнера, PKCS#12-KDF на SHA-1/Стрибоге/ГОСТ Р 34.11-94; ГОСТ 28147 в ECB/CBC/CFB/
    гамме; восемь узлов замены) осмысленного PKCS#8 не дал — разбор этого PBE отдельная задача.
    Практический вывод: наш `.pfx` — для мира OpenSSL/gost-engine; для КриптоПро остаётся `topfx`
    через `certmgr`.

  ревью, затем `@codex review`, затем ещё 15 минут. Если и после этого тишина — сними состояние
  Codex (ниже) и мержи зелёный PR без ревью, оставив в нём комментарий с причиной и снятыми
  показаниями. Правило «не мержить с неотвеченными замечаниями» касается пришедших замечаний, а
  не бессрочного ожидания недоступного сервиса.
- Диагностика без браузера, если и ручной вызов молчит: токен из `~/.codex/auth.json`
  (`Authorization: Bearer <tokens.access_token>` + `ChatGPT-Account-Id: <tokens.account_id>`),
  дальше `GET https://chatgpt.com/backend-api/wham/usage` — план, лимиты, credits;
  `.../wham/github/installations` — установка GitHub App. Полю `review_preference` из
  `.../wham/settings/code_review` не верь: там у всех 56 репозиториев стоит `never` с пустым
  `updated_at`, хотя ревью при этом исправно приходит.

## Первый шаг для следующего агента

Пассивные production-пути закрыты: Рутокен S, Рутокен Lite, JaCarta LT и ESMART
снимаются по отдельным APDU-бэкендам. S/LT 26–27.08.2026 и оба ESMART 27.08.2026
прошли строгий физический E2E на синтетических неэкспортируемых двухключевых
контейнерах до HDIMAGE и PFX (пп. 41–42). Не возвращай S к `rtCOMLite`, не
маршрутизируй LT через PRO/Lite-протокол и не отправляй ESMART APDU без строгих
PKCS#11-свидетельств ISBC и точного проверенного семейства reader.

**Рутокен ЭЦП** (п. 22–23, 25) остаётся отдельной отрицательной границей:
PKCS#11 отдаёт публичный сертификат без PIN, но закрытый ключ аппаратно неизвлекаем.

**По Рутокен ЭЦП вопросов к железу не осталось** (п. 25, сеанс 12.08.2026): блоб `CKO_DATA` снят,
разобран и оказался цепочкой сертификатов УЦ без ключевого материала, гипотеза эталонной пары
опровергнута, боевой контейнер средствами CSP не копируется. **Не планируй сеанс с ЭЦП заново** —
дамп со всеми объектами лежит локально в `token-session\session\`, разбирать его можно оффлайн.
Направление «разбор `CKO_DATA` в шесть `*.key`» закрыто: собирать не из чего.

**Сеанс 13.08.2026 добавил третью модель — Рутокен ЭЦП 3.0** (пп. 27–31). Он не сводится к 2.0:
КриптоПро обслуживает его как ФКН и ключ с диска на него не пишет, а `rtCOMLite::ReadBinary` на нём
рушил процесс — из-за этого `list` падал с `0xC0000374` на любой машине с воткнутым 3.0. Оба дефекта
(падение и потеря сертификата без парного контейнера) исправлены и проверены на живом железе; тезис
«публичные объекты PKCS#11 читаются без PIN» перепроверен прямым опытом на 3.0 и на Lite.

**Тот же сеанс добавил четвёртую модель и первого чужого вендора — JaCarta** (пп. 32–35). Главное:
одна библиотека PKCS#11 показывает только своего вендора, поэтому JaCarta не попадала в
`deps`/`list`/`token` вообще; теперь загружаются обе известные библиотеки. Снятие ключа с JaCarta
проверено полностью (п. 35, PIN дал владелец): штатные пути (`keycopy`/`certmgr`/PKCS#11) дают
`0x8009000b`, но это политика CSP — **APDU-разбор показал пассивный носитель, и закрытый ключ снят
по APDU** (восстановлен офлайн, `d·G==Q`; поле `[0]` неэкспортируемого `primary.key` содержит
ключ). Метод и разбор — `docs/apdu/jacarta-pro.md`. Заодно там же рецепт, как не обмануться:
контейнер с уже снятым запретом копируется с любого носителя, и на нём проверять бессмысленно.

Незакрытое по токенам: отдельный production-бэкенд для исследованной JaCarta PRO;
JaCarta-2 ГОСТ и eToken — только при появлении точного живого носителя.

Для будущей регрессии на S/LT/ESMART не копируй готовый экспортируемый ключ: создавай контейнер
прямо на точном reader, сначала доказывай отсутствие `CRYPT_EXPORT`, а после E2E удаляй
только своё синтетическое имя. Рутокен ЭЦП и пользовательские контейнеры не трогать.
