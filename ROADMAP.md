## 2. Приоритетный план

> **Внешние NuGet-пакеты в `Core` и `App` разрешены** (решение владельца, 06.08.2026). Прежний запрет
> был главным ограничением: он закрывал и ГОСТ-криптографию, и PKCS#11. Планы ниже это учитывают.
> Цена решения — размер портативного exe и цепочка поставки, поэтому пакеты берём точечно.

### P0 — вернуть работоспособность на реальном железе
Сейчас у владельца утилита не может снять контейнер ни с одного имеющегося токена.

- [ ] **Рутокен Lite/ЭЦП через PKCS#11.** `Pkcs11Interop` + системная `rtPKCS11ECP.dll` от «Актив».
      Это единственный путь к Lite: rtCOMLite отдаёт структуру каталогов, но не файлы (AGENTS п. 20).
      Шаги: перечисление слотов и токенов → `C_Login` пользовательским PIN → поиск объектов контейнера
      КриптоПро (они лежат как `CKO_DATA` с меткой контейнера) → сборка тех же шести `*.key`.
      Дальше конвейер уже работает. **Риск:** раскладка data-объектов КриптоПро не документирована,
      возможен упор в тот же тупик, что и с rtCOMLite, — проверять на железе рано и малой кровью.
- [ ] **Починить релизную автоматику CI.** Джоб публикации переведён на self-hosted раннер `adler`,
      где нет `gh`, и падает на каждом теге (релиз v1.3.1 пришлось выкладывать вручную из артефакта CI).
      Варианты: переменная репозитория `CI_RUNS_ON = ["ubuntu-latest"]` (предусмотренный override),
      установка `gh` на раннер, либо вызов REST API через `curl` вместо `gh`.
- [ ] **E2E-тест на физическом Рутокене S.** Единственный сценарий, где ожидаемо работает rtCOMLite.
      Проверить: `ReadAllContainers` возвращает 6 `.key`; маппинг имён совпадает с реальной раскладкой.
      **Без железа не закрыть**, и оно есть не у всех — поэтому ниже приоритета PKCS#11.
- [x] **E2E на Рутокен Lite** — прогнано. Найдено и исправлено падение процесса на `EnumFolders()`/`EnumFiles()`
      (порча кучи в rtCOMLite, AGENTS п. 19); авторизация по PIN и обход каталогов работают.
      Итог по устройству: файлы контейнеров на Lite через rtCOMLite не видны (AGENTS п. 20).
- [x] **Снятие запрета end-to-end** — проверено: `header.key` 1245 → 3075 байт, ключ стал экспортируемым.
- [x] **Конвертация в PKCS#12 (.pfx)** — через `certmgr` (у `p12utility` 4.0.8 нет режима `--cptop12`,
      есть только обратный `--p12tocp`). Команда `topfx`, кнопка «Экспорт в PFX».

### P1 — путь без КриптоПро CSP
Что уже проверено и где именно стоит стена — в разделе 3. Порядок важен: пункты идут по зависимостям.

- [ ] **Разобрать защиту `masks.key`.** Ключевой блокер. Проверено: простое `primary · mask⁻¹ mod q`
      открытый ключ не воспроизводит (раздел 3), значит между файлами и ключом стоит вывод ключа и
      расшифрование маски на ГОСТ-примитивах. Гипотеза для проверки первой: маска зашифрована на ключе,
      выведенном из пароля контейнера (даже пустого) через Стрибог, 12-байтовое поле — UKM/синхропосылка,
      4-байтовое — контрольная сумма. Инструмент проверки уже есть и стоит секунды на гипотезу.
- [ ] **Извлечение закрытого ключа без CSP** → вывод в PKCS#8/PEM для OpenSSL с gost-engine.
      Само снятие маски после разбора — обычная арифметика `BigInteger`, ГОСТ-примитивы там не нужны.
      Побочный выигрыш: при своём разборе **«снятие запрета на экспорт» не нужно вовсе** — флаг
      `CRYPT_EXPORT` в `header.key` существует только для CSP и на сам ключ не влияет.
- [ ] **Сборка PKCS#12 своими силами** (BouncyCastle: ГОСТ Р 34.10-2012, Стрибог, GOST 28147).
      Снимает зависимость от `certmgr`, то есть от установленного CSP, на последнем шаге конвейера.
- [ ] **Извлечение сертификата без CSP.** Проверено: открытым DER в `header.key` его нет ни в одном из
      трёх реальных контейнеров. Раз `CryptGetKeyParam(KP_CERTIFICATE)` его оттуда достаёт, он хранится
      сжатым или в нестандартной обёртке — нужен разбор структуры `header.key`.

## 3. Путь без КриптоПро CSP — что проверено

Разбор от 06.08.2026 на реальных контейнерах. Здесь только проверенное, чтобы следующий заход
не начинал с нуля и не повторял тупики.

**Что от CSP уже не зависит.** Снятие контейнера с токена: в `RutokenExporter` нет ни одного вызова
CryptoAPI. Это единственная готовая CSP-free ветка.

**Что завязано жёстко.** `p12utility.win32.exe` не линкуется ни с одной библиотекой КриптоПро (импорт
только ADVAPI32, CRYPT32, KERNEL32, msvcrt, USER32), но внутри есть импорт `CryptAcquireContext` и
строки `Crypto-Pro` — значит идёт к провайдеру через CryptoAPI. `certmgr.exe` берётся из папки
установки CSP. Весь `CertFromContainer` — CryptoAPI. То есть без CSP не работают снятие запрета,
экспорт в PFX, перечисление контейнеров и извлечение сертификата.

**Структура контейнера (проверена на реальных файлах):**
`primary.key` = `SEQUENCE { OCTET STRING (32) }`;
`masks.key` = `SEQUENCE { OCTET STRING (32), OCTET STRING (12), OCTET STRING (4) }`;
`name.key` = имя контейнера в cp1251. Раскладка ГОСТ Р 34.10-2012, 256 бит.

**Главный проверенный результат — отрицательный.** Широко повторяемая формула `d = primary · mask⁻¹ mod q`
открытый ключ **не воспроизводит**. Проверено на контейнере с кривой `1.2.643.2.2.36.0`
(CryptoPro-A/XchA, алгоритм `1.2.643.7.1.1.1.1`): перебраны обе пары ключей, оба порядка байт для
`primary` и для маски, все три поля `masks.key` и варианты `p·m⁻¹`, `p·m`, `p⁻¹·m`, `m·p⁻¹`, а также
«маски нет вовсе» — ни одна комбинация не дала точку `Q` из сертификата.

Отрицательный результат опирается на самопроверку математики, а не на веру: `q·G` даёт точку на
бесконечности (это подтверждает параметры кривой и реализацию умножения), а `Q` из сертификата лежит
на кривой (это подтверждает выбор кривой и порядок байт `Q`). Контейнер при этом без пароля: тихий
`CryptAcquireContext` с `CRYPT_SILENT` проходит, `KP_PERMISSIONS` читается.

**Вывод:** маска в `masks.key` не пригодна напрямую — между файлами и закрытым ключом стоит вывод
ключа и расшифрование на ГОСТ-примитивах, даже когда пароля на контейнере нет. Это меняет оценку
работ: CSP-free путь — это не «немного арифметики», а сначала разбор схемы защиты (P1).

**Инструмент проверки** лежит в истории этой работы и восстанавливается за минуты: посчитать `d·G`
на кривой из сертификата и сравнить с `Q` оттуда же. Любая новая гипотеза проверяется за секунды —
начинать надо с неё, а не с реализации.

## 4. Ограничения и риски
- **Рутокен ЭЦП 2.0** (аппаратный неизвлекаемый ключ) не поддерживается в принципе — как и оригинальный `Tokens.exe`. Ключ физически не покидает чип.
- **Кодировки.** `name.key` и `PP_ENUMCONTAINERS` — cp1251; при работе с именами не использовать `Encoding.Default` (в .NET это UTF-8). Есть `Cp1251`. Вывод в перенаправленный stdout тоже cp1251, справка `p12utility` — cp866.
- **Битность — только x86.** `rtCOMLite.dll` 32-битный и грузится в процесс без регистрации; в x64 он работал бы лишь через зарегистрированный COM-суррогат, то есть требовал бы установки компонента. Перевод проекта на x64/AnyCPU сломает главную идею упаковки. `p12utility.win32.exe` тоже 32-битный, но запускается отдельным процессом.
- **Кэш зависимостей** — `%LOCALAPPDATA%\CryptoProExport\bundled\<версия>`. Ключ по версии сборки: после апдейта файлы перераспаковываются, старые каталоги не чистятся автоматически.
- **PIN-поток.** Сейчас: если PIN дефолтный — `12345678`; если задан — из поля; иначе `AuthenticateOwnerFromGUI`. На нестандартных сценариях (заблокированный PIN) — проверить ветку разблокировки (`unblockToken` в исходном `tokens.hta` не портирован).
