# JaCarta PRO на уровне APDU — разбор 13.08.2026

> Сеанс с живым носителем `Aladdin Token JC 0` (JaCarta PRO «PROFELTORG», серийный
> `00A7A257`, ATR `3B D5 18 00 81 31 FE 7D 80 73 C8 21 10 F4`, платформа eToken PRO
> Java 72K OS755). PIN владельца получен ранее (лежит в `secrets.txt`). Работал только со
> своим считывателем, чужие токены не трогал.

## Итог (главное)

**Доказано прямым опытом:** JaCarta PRO с апплетом CryptoPro — **пассивный носитель**.
Подпись ГОСТ считается **на хосте** (в трассе нет ни одной on-card крипто-команды), а
ключевые файлы `primary.key`/`masks.key` карта отдаёт на хост по READ **даже для
неэкспортируемого ключа** (`SW=9000`). Запрет на экспорт формирует программа CSP
(`keycopy.c`), карта чтение ключевых файлов не блокирует.

**Доказано построением (13.08.2026, дополнение):** снятых байт **достаточно** — закрытый ключ
неэкспортируемого контейнера восстановлен офлайн и сверен с открытым ключом. Раскрыт формат
поля `[0](32)`: **в нём и лежит зашифрованный закрытый ключ**, а восстановление —
`d = decrypt(storageKey, [0]) · маска⁻¹ mod q`, где `storageKey` выводится из **пустого**
пароля и соли (KDF на Стрибог-256), а PIN `1122` — это доступ к карте, а не пароль файлового
шифрования. Проверено на двух своих тестовых контейнерах: `jcrec` (сверено с полным
экспортированным `Q` — и X, и Y) и `jcnx` (сверено с 8-байтовым отпечатком X из `header.key`).
Никакого card- или session-производного секрета в преобразовании нет — иначе офлайн-реконструкция
не сошлась бы. Детали — раздел «Разбор поля `[0](32)` и восстановление `d`».

Итог по матрице: для JaCarta PRO (этот экземпляр, апплет CryptoPro) **закрытый ключ ГОСТ, даже
помеченный неэкспортируемым, извлекаем на уровне APDU** — пассивный носитель, ключевые файлы
снимаются с карты, `d` восстанавливается офлайн. Прежнее «проверенными способами не снимается»
для этой модели снято. (В отличие от Рутокен ЭЦП/ЭЦП 3.0 — активный носитель, ключ в чипе,
`CKA_EXTRACTABLE=false` аппаратно.)

## Как снята трасса

CSP идёт к карте через системный PC/SC: `cpscard.dll` → `pcsc.dll` → `winscard.dll`
(Windows) → `SCardSvr` → драйвер ридера. `pcsc.dll` импортирует полный набор `SCard*`
(`SCardConnectW`, `SCardTransmit`, `SCardBeginTransaction`, …) из системного
`winscard.dll` — значит перехват на `winscard.dll` видит **все** APDU. Реализованы два
независимых перехватчика, дающих одинаковый результат:

- **Нативный winscard-прокси** (`harness/proxy.c` + `harness/build.ps1`, x64). `winscard.dll`,
  форвардящий все экспорты в копию `winscard_real.dll`, кроме хука `SCardTransmit` — тот логирует
  APDU (данные VERIFY/CHANGE REFERENCE DATA маскируются) и вызывает настоящий. `build.ps1` собирает
  его MSVC (`cl`), а при отсутствии BuildTools — MinGW-w64 (`gcc` через `.def`). Кладётся рядом с
  копией `csptest.exe`; loader берёт `winscard.dll` из каталога exe первым. Им сняты файлы `jcrec`
  для реконструкции. Для .NET-хостов (apphost жёстко ищет DLL) прокси грузится через `NativeLibrary.Load`.
- **Frida** (`pip install frida-tools`) — быстрый динамический хук `SCardTransmit`/`SCardConnectW`/
  `SCardBeginTransaction`/`SCardStatusW` в `csptest.exe` без сборки; Python-драйвер спавнит
  `csptest`, снимает лог и stdout (cp866).

Всё — только чтение и штатные операции CSP; APDU не инжектировались, карта не перепрошивалась.
Сырые трассы **не коммитятся**: в них персональные данные (боевой сертификат, зашифрованный
`primary.key` реального владельца). В репозиторий попадают только байты выброшенных тестовых
контейнеров `jcnx`/`jcrec` и инструменты.

Всё — только чтение и штатные операции CSP; APDU не инжектировались, карта не
перепрошивалась.

## Протокол апплета CryptoPro на JaCarta

CSP перебирает AID (`00 A4 04 00 …`), большинство даёт `6A82/6A86`, откликается апплет
**`A0000003120202`** (FCI `6F10 8407 A0000003120202 A505 9F6502 0212`). Дальше:

| APDU | Смысл |
|------|-------|
| `00 A4 04 …` / `00 A4 08 …` | SELECT апплета / SELECT по пути (DF/EF) |
| `00 CA <tag>` | GET DATA — паспорт носителя, серийник, параметры |
| `80 18 00 00 04 0E02 <off> 00` | READ — чтение содержимого EF кусками по смещению |
| `80 15 00 00 <Lc> 0E02 0000 10 <len> <data>` | WRITE — запись EF (в т.ч. remask) |
| `80 07 …` / `80 17 00 00 08` / `80 11 …` | Триплет взаимной аутентификации по PIN (GET CHALLENGE → ответ). PIN **открытым текстом по проводу не идёт** |

Файловая раскладка контейнера (директория `66665000 / E00E0B00 / CC0<n>`, где `CC00`,
`CC01`, `CC02`… — контейнеры по порядку; внутри файлы `F00x`):

| EF | Содержимое |
|----|------------|
| `F001` | `masks.key` — `SEQUENCE { OCTET STRING(32) маска, OCTET STRING(12) соль KDF, OCTET STRING(4) КС }` |
| `F002` | `primary.key` — закрытый ключ (формат зависит от экспортируемости, см. ниже) |
| `F003` | сертификат / открытый ключ (DER) |
| `F006` | `name.key` — имя контейнера |
| `F00F` | 20-байтовый служебный блок (заголовок/хеш) |

Раскладка `F001`/`F002` дословно совпадает со структурой файлового контейнера КриптоПро из
`ROADMAP.md` §3.1 (`masks.key` = 32+12+4, `primary.key` = `SEQUENCE{OCTET STRING(32)}`).
То есть на JaCarta лежит **обычный файловый контейнер CryptoPro**, просто в файловой системе
смарт-карты, а не на диске.

## Три эксперимента

Все — на считывателе `Aladdin Token JC 0`, PIN подавался как `-pinsrc`/`-password`
(challenge-response, попытки PIN успех не тратит).

### 1. keycopy экспортируемого контейнера токен→HDIMAGE — код 0

Существующий контейнер-копия (боевой ключ с уже взведённым `CRYPT_EXPORT`). CSP снял
`primary.key` и `masks.key` **открытым APDU** после PIN-сессии:

```
SELECT …CC00F002 ; READ → 30 22 0420 <32B зашифрованный primary>            ← primary.key
SELECT …CC00F001 ; READ → 30 36 0420 <32B маска> 040C <12B соль> 0404 <4B КС> ← masks.key
… затем WRITE …F002 / …F001 новыми значениями (remask)
```

`primary.key` экспортируемого ключа — ровно `SEQUENCE{OCTET STRING(32)}`. Вместе с маской и
KDF из §3.1 число `d` восстанавливается офлайн (это и есть легитимный бэкап владельца).
Конкретные байты боевого ключа здесь не приводятся.

### 2. keycopy неэкспортируемого контейнера — `0x8009000b`, но карта ключ отдала

Сгенерировал на носителе свой тестовый контейнер `jcnx` (оба ключа созданы на карте →
несут запрет: `KP_PERMISSIONS` без `CRYPT_EXPORT`). `csptest -keycopy` упал:

```
keycopy.c:331: CopyPrivateKey(AT_KEYEXCHANGE)
Error 0x8009000b (NTE_BAD_KEY_STATE)
```

**Но отказ бросил CSP, а не карта.** В той же трассе карта на READ отдала оба ключевых файла
с `SW=9000` (тестовый ключ `jcnx`, персданных нет, контейнер уже удалён):

```
SELECT …CC02F002 ; READ → 30 44 0420 ED09D5A5244C02D0F71B361BDE1FA72AFD29C6BF867BE3A0392FE2F1DBC5BC75
                          80 20 EED9A5789F642A1A1ABD03CFB136FCF7D646020AEA333E1437D97C70347CE2AB
SELECT …CC02F001 ; READ → 30 36 0420 ADF4166647178A023958F128EE9A3102133C0168946B217E22E556ED2981AD7F
                          040C 13368456DE015B3FCFF62D82 0404 D2C35C84
```

Отличие формата: у **неэкспортируемого** `primary.key` — `SEQUENCE { OCTET STRING(32),
[0] (32) }`, лишнее 32-байтовое поле `[0]` против `SEQUENCE{OCTET STRING(32)}` у
экспортируемого. Но и оно уходит с карты. Карта чтение файлов ключа **не блокирует**.

### 3. Подпись неэкспортируемого `jcnx` — код 0, подпись считается на хосте

`csptest -keyset -sign GOST12_256 -container …\jcnx` — код 0, `.sig` 64 байта (ГОСТ-256).
В трассе:

- карта снова отдаёт `…CC02F002` (primary) и `…CC02F001` (masks) на хост;
- затем `80 15` — remask (перезапись F002/F001 новыми значениями);
- **ни одной on-card крипто-команды**: во всей трассе только `00A4` (SELECT), `00CA`
  (GET DATA), `8018` (READ), `8015` (WRITE), `8007/8017/8011` (аутентификация). Команд PSO
  `00 2A`, MSE `00 22`, INTERNAL AUTHENTICATE `00 88` — **нет вовсе**.

Значит хеш сообщения и умножение на закрытый ключ считает CSP на хосте, а карта закрытым
ключом не оперирует. Это определение **пассивного носителя**: приватная операция требует
чтения `primary.key`+`masks.key` на хост при каждом использовании.

## Вывод

- **Носитель пассивный.** JaCarta PRO (этот экземпляр, апплет CryptoPro) — зашифрованное
  файловое хранилище + PIN-замок + remask. Закрытый ключ ГОСТ не считается на чипе; при
  каждой подписи `primary.key`+`masks.key` уходят на хост, и CSP там же вычисляет подпись.
- **Запрет на экспорт — только политика CSP.** Карта отдаёт `F001/F002` любой
  PIN-аутентифицированной сессии независимо от `CRYPT_EXPORT`; `0x8009000b` формирует
  клиент (`keycopy.c`). Аппаратной защиты чтения ключевых файлов нет.
- **Следствие — доказано построением.** Снятых байт достаточно: закрытый ключ
  неэкспортируемого контейнера восстановлен офлайн (`d = decrypt(storageKey, [0]) · маска⁻¹`,
  пустой пароль KDF) и сверен с открытым ключом на двух контейнерах. Card-/session-производного
  секрета в преобразовании нет. Раздел «Разбор поля `[0](32)`».

Контраст: у Рутокен ЭЦP/ЭЦП 3.0 при подписи ключ с карты не выходит (активный носитель, счёт
в чипе) — там APDU-путь закрыт по существу. У JaCarta PRO аппаратной стены нет **и** снятых
байт достаточно для офлайн-восстановления — ключ извлекаем.

## Разбор поля `[0](32)` и восстановление `d`

Форматы `primary.key` различаются экспортируемостью:

| Ключ | `primary.key` | Где зашифрованный закрытый ключ |
|------|---------------|---------------------------------|
| экспортируемый | `SEQUENCE { OCTET STRING(32) }` | сам `OCTET STRING` |
| **неэкспортируемый** | `SEQUENCE { OCTET STRING(32) A, [0] B(32) }` | **поле `[0]` (B)** |

То есть у неэкспортируемого ключа зашифрованный ключ **переехал** в тег `[0]`, а на месте
`OCTET STRING` появилось отдельное значение `A`. Восстановление — тем же алгоритмом, что для
файлового контейнера (ROADMAP §3.1), но из поля `[0]`:

```
storageKey = CPKDF(пароль="", соль из masks.key)          # KDF на Стрибог-256, 2 итерации
primDec    = ГОСТ-28147-ECB-decrypt(storageKey, B)         # узел Param-Z
d          = LE(primDec) · LE(маска)⁻¹  mod q               # q — порядок кривой
```

**Ключевые факты, найденные экспериментом:**
- зашифрованный ключ — в поле `[0]` (B), **не** в `OCTET STRING` (A); `decrypt(A)·маска⁻¹` и
  прочие комбинации с `A` числа `d` не дают — `A` не на пути восстановления (его точная роль —
  открытый под-вопрос: не ключ, не маска, не открытый ключ);
- **пароль KDF — пустой**, хотя контейнер создан с `-password 1122`. Значит `1122` — это PIN
  доступа к карте (challenge-response), а файловое шифрование контейнера идёт с пустым паролем,
  как и у боевых файловых контейнеров владельца (ROADMAP §3.1);
- card- или session-производного секрета в преобразовании нет — офлайн-реконструкция без токена
  сходится.

**Проверка на двух своих тестовых контейнерах (оба удалены после опыта):**

| Контейнер | Оракул | Результат |
|-----------|--------|-----------|
| `jcrec` | экспортированный `Q` (csptest `-export`), сверка X **и** Y | `d·G.X == Q.X`, `d·G.Y == Q.Y` ✅ |
| `jcnx`  | 8-байтовый отпечаток X из `header.key` (тег `8B`) | `X_le[0..8] == 0AA12D0B7A9FDE24` ✅ |

```
jcrec d = 82DE5313E1E8BC292C70947DF429BE9A3D2A1DB90309AE3A0C4669FA938F76F4
jcnx  d = FF1ECB27F52CACD51B7284453EBF9C0C55C069526AE7F43A10541DBD317ABC3B
```

Пробник реконструкции — `harness/recon/` (BouncyCastle 2.7.0; ГОСТ-примитивы совпадают с
`ContainerKeyExtractor`/`GostContainerCrypto` из ветки CSP-free разбора файловых контейнеров).
`ContainerKeyExtractor.ParsePrimary` сейчас принимает только экспортируемый формат (32-байтовый
`OCTET STRING`); чтобы разбирать снятые с JaCarta неэкспортируемые контейнеры, его надо
расширить на форму `SEQUENCE { OCTET STRING, [0] }`, беря ключ из поля `[0]`.

## Что осталось

- **Роль поля `A`** (`OCTET STRING` неэкспортируемого `primary.key`): не ключ и не маска;
  вероятно контрольное значение или копия под другим ключом. Для извлечения ключа не нужно.
- **Расширить `ContainerKeyExtractor`** на неэкспортируемый формат (поле `[0]`) и собрать PKCS#12,
  чтобы снятый с JaCarta ключ доходил до `.pfx` штатным конвейером.
- **JaCarta-2 ГОСТ** (другая модель, аппаратный ГОСТ — ожидается активный носитель) и
  **Рутокен Lite** (смарт-карта, статус «проверенными способами не снимается») — прогнать тем же
  APDU-методом на живом носителе с неэкспортируемым контейнером.

## Воспроизведение

```powershell
# 1. Хук APDU (frida-tools в Python 3.14): trace.py спавнит csptest, apdu_trace.js хукает winscard
python trace.py <log> -- "C:\Program Files\Crypto Pro\CSP\csptest.exe" `
    -keycopy -contsrc "\\.\Aladdin Token JC 0\<контейнер>" -contdest "\\.\HDIMAGE\<копия>" -pinsrc <PIN> -silent

# 2. Свой неэкспортируемый контейнер на носителе (ключ генерируется на карте)
pwsh token-session\make-token-container.ps1 -ContainerPath '\\.\Aladdin Token JC 0\jcnx' -Password <PIN>

# 3. Трасса подписи — доказать пассивность (нет on-card sign, primary/masks уходят с карты)
python trace.py <log> -- "C:\Program Files\Crypto Pro\CSP\csptest.exe" `
    -keyset -sign GOST12_256 -container "\\.\Aladdin Token JC 0\jcnx" -keytype exchange -password <PIN> -in in.bin -out out.sig -silent

# Уборка: удалить тестовый контейнер и копии
csptest -keyset -deletekeyset -container "\\.\Aladdin Token JC 0\jcnx" -password <PIN>
```

**Правовая рамка.** Работа ведётся владельцем со своими ключами (легитимный бэкап). Сырые
APDU-трассы содержат персональные данные и в репозиторий не попадают; здесь приведены только
байты выброшенного тестового контейнера `jcnx` и структура протокола.
