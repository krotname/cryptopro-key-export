# MS_KEY K «АНГАРА» (БИФИТ/МультиСофт) — APDU-уровень: контейнер КриптоПро читается мимо CSP

Отчёт по сеансу 02.09.2026. Носитель — `BIFIT ANGARA 0`, USB `VID_23A0&PID_0008`,
ATR `3B 9E 96 00 80 31 C0 65 4D 53 00 00 00 72 F7 41 81 07`, модель `P5CC081`, vendor
`MultiSoft`, MS_KEY K Исп.8.1.1. КриптоПро CSP 5.0.13800 на ADLER-LENOVO.

## Главный вывод

**Файловый контейнер КриптоПро физически лежит в файловой памяти MS_KEY K и полностью читается
по APDU.** КриптоПро работает с носителем как с пассивной картой памяти: приложение `MSKEYKC`,
внутри — DF контейнера и обычные `SELECT` / `READ BINARY`. Карточных крипто-команд в обмене нет
(`00 2A`/PSO и любой sign-INS отсутствуют) — всю криптографию CSP считает на стороне хоста,
прочитав `primary.key` (маскированный закрытый ключ) и `masks.key` (маска+соль+CRC). Это тот же
класс, что Рутокен Lite и JaCarta LT: ключ **не ФКН** и восстанавливается офлайн.

Подтверждено тремя независимыми способами:

1. **Трасса самого CSP** — прокси-`winscard.dll` (харнесс `docs/apdu/harness/`) перехватил APDU,
   которыми `csptest -keyset -newkeyset/-makecert/-check` создаёт и использует контейнер. В обмене
   видны только `SELECT`/`READ BINARY`/`GET DATA`/`VERIFY`/`UPDATE BINARY` — ни одной команды
   подписи на карте.
2. **Собственный съём** — независимый PC/SC-ридер (без КриптоПро) прошёл ту же последовательность
   и прочитал те же EF контейнера.
3. **Восстановление закрытого ключа** — из прочитанных по APDU `primary.key` + `masks.key`
   офлайн-разбором (`ContainerKeyExtractor`, BouncyCastle) вычислен закрытый ключ `d`, и `d·G`
   **совпал** с открытым ключом `Q` из сертификата (кривая `1.2.643.2.2.35.1`). Байтовое
   подтверждение, что снятый материал — рабочий ключ.

Проверка выполнена на **синтетическом** контейнере `cpxt_test`, созданном самим агентом
(`protected=none`), — боевые контейнеры владельца не затрагивались. Синтетический контейнер удаляется
после проверок (`csptest -keyset -deletekeyset`).

## Разрешённое противоречие (создаёт ли CSP контейнер)

В проекте были два прямо противоположных факта. Проверка построением на живом железе:

```
csptest -keyset -enum_cont -verifycontext -fqcn                     # BIFIT пуст (до создания)
csptest -keyset -newkeyset -container '\\.\BIFIT ANGARA 0\cpxt_test' -provtype 80 -protected=none
csptest -keyset -container  '\\.\BIFIT ANGARA 0\cpxt_test' -provtype 80 -makecert
csptest -keyset -enum_cont -verifycontext -fqcn                     # \\.\BIFIT ANGARA 0\cpxt_test
```

**CSP контейнер СОЗДАЁТ**, оба ключа (signature + exchange) генерируются на носителе, сертификаты
`-makecert` пишутся в контейнер, и он виден в `enum_cont`. Совпадает с `docs/hardware/bifit.md`.
Прежняя запись памяти «CSP контейнеров не создаёт» была ошибочной (вероятно, из-за bash-квотинга
`\\.\`: в PowerShell та же команда отрабатывает штатно).

## Метод: прокси-`winscard.dll`

MS_KEY ходит к карте через системный `winscard.dll` (CCID-класс, Microsoft Usbccid), поэтому APDU
перехватывается подстановкой прокси в каталог рядом с `csptest.exe` (тот же харнесс, что для Рутокена
и ESMART: `docs/apdu/harness/`, сборка `build.ps1`, лог по `WINSCARD_TRACE_LOG`). Грабли —
в памяти `apdu-trace-harness`: пустой `DllMain`, ANSI-логирование, форвардеры через `#pragma /EXPORT`.

## Протокол файлов контейнера

| Операция | APDU | Комментарий |
|----------|------|-------------|
| SELECT приложения | `00 A4 04 0C 07  4D 53 4B 45 59 4B 43` | по имени DF — `MSKEYKC` |
| SELECT DF контейнера | `00 A4 00 0C 02  00 <base>` | `base` ∈ {01, 11, 21, …}, шаг 0x10 |
| SELECT EF | `00 A4 00 04 02  00 <ef>` | P2=04 — вернуть FCP; `ef = base + offset` |
| READ BINARY | `00 B0 <offHi> <offLo> <Le>` | чтение содержимого EF, чанк ≤255 |
| VERIFY | `00 20 00 7D <Lc> <ascii>` | ссылка доступа контейнера P2=**0x7D** |
| UPDATE BINARY | `00 D6 …` | CSP переписывает primary/masks при **ротации маски** |
| FCP EF | шаблон `62 xx … 80 <1..2> <size> …` | тег `80` — число байт содержимого |

**Раскладка контейнера.** Каждый контейнер — DF `00<base>`; шесть логических `*.key` — это EF
`00<base+offset>`. Соответствие установлено **по содержимому** (ASN.1), а не по догадке:

| offset | EF (base=01) | Размер (cpxt_test) | Содержимое (ASN.1) | Логический файл | PIN |
|--------|--------------|--------------------|--------------------|-----------------|-----|
| +0x00  | `00 01` | 54  | `SEQ { OS32, OS12, OS4 }` | **masks.key** (маска+соль+CRC) | нужен VERIFY |
| +0x01  | `00 02` | 68  | `SEQ { OS32, OS32 }`      | **primary.key** (маскир. ключи) | нужен VERIFY |
| +0x02  | `00 03` | 1311| большой `SEQ` (header.key + сертификат X.509) | **header.key** | без PIN |
| +0x05  | `00 06` | 11  | `SEQ { IA5String(имя) }`  | **name.key** | без PIN |

`name.key` и `header.key` читаются **без авторизации** (по ним CSP и перечисляет контейнеры);
`primary.key` и `masks.key` — после `VERIFY 00 20 00 7D`. Файлы дополнены до размера FCP нулями
(на диске у КриптоПро — чистый DER), лишний хвост обрезается до конца первого ASN.1-объекта.

**Пустые слоты.** Носитель держит предвыделенные слоты (DF 11, 21, …) с EF из одних нулей. Настоящий
контейнер отличается тем, что `name.key` — валидный `SEQUENCE` с непустым именем; ридер пустые слоты
отбраковывает (`MsKeyAngaraApdu.IsDerSequence`).

## VERIFY и счётчик (осторожно, необратимо)

Ссылка доступа контейнера — **P2=0x7D**, это **не** пользовательский PIN устройства (`C_Login`) и не
PIN-код носителя. У проверенного экземпляра PIN устройства не задан (`protected=none`), и для доступа
к файлам контейнера CSP посылает **транспортное `11111111`** (наблюдено немаскированной трассой
одноразового прокси; значение заведомо верно — карта отвечает `9000`, повтор счётчику не угрожает).
Для контейнера с реальным паролем по ссылке 0x7D пойдёт другой секрет, и слепой ввод сожжёт попытку:
**10 неверных блокируют устройство навсегда** — PIN и пароли не подбирать (память
`bifit-mskey-ibank2key`). Пароль контейнера для снятия маски (CPKDF) — отдельная величина; у
`protected=none` он пуст.

## Снятие маски — доведено и проверено (`d·G == Q`)

Из `primary.key` + `masks.key`, прочитанных по APDU, закрытый ключ восстановлен
`ContainerKeyExtractor` (та же процедура, что для файловых контейнеров и Рутокен Lite:
CPKDF/Стрибог-256 → ГОСТ 28147-89 ECB Param-Z → `d = primary · mask⁻¹ mod q`) и **сошёлся с
сертификатом**: `d·G` дал ровно точку `Q` из `header.key`. Значение `d` в отчёт и репозиторий не
выносится. `primary.key` здесь имеет форму `SEQ{OS32,OS32}` (обе половины пары ключей под общей
маской) — экстрактор перебирает оба кандидата и берёт тот, чей `d·G` совпал с сертификатом.

## Реализация в проекте

- `Core/MsKeyAngaraApdu` — read-only ридер контейнера по APDU (PC/SC), протокол выше. Команды
  создания/удаления/записи не отправляет. Заведён в общий роутер `DirectTokenApdu`
  (`RutokenKind.Bifit`), гейт — имя считывателя `ANGARA` (не iBank2Key) **и** `9000` на SELECT
  `MSKEYKC` (у iBank2Key приложения нет).
- CLI `angaraexport <reader> <outDir> [pin]` — перечисляет контейнеры (`name.key`, без PIN), снимает
  их по APDU и восстанавливает ключ в `private.pem`. Без `pin` берётся транспортный `11111111` из
  реестра `StandardPins` (только для `protected=none`).
- Юнит-тесты (без железа) — `tests/…/MsKeyAngaraApduTests`: раскладка DF/EF, разбор FCP, отбраковка
  пустых слотов, гейт семейства.

## Оговорки

- **Персональные данные.** У боевого контейнера `header.key` содержит реальный сертификат владельца,
  а `primary/masks` — его закрытый ключ. Сырые трассы и снятые файлы боевых контейнеров в репозиторий
  не выносить. Здесь всё проверено на синтетическом `cpxt_test`.
- Прокси **маскирует** `VERIFY`/`CHANGE REFERENCE DATA`; немаскированный прокси применялся однократно
  локально только чтобы снять транспортное значение `protected=none` и не публиковался.
- Не путать с ESMART Token ANGARA (ISBC) и `esmart_token_angara_mod.dll` — другая линейка.
