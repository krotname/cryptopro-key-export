# Рутокен Lite (прошивка 9.02) — APDU-уровень: контейнер КриптоПро читается мимо CSP

Отчёт по сеансу 13.08.2026. Токен — `Aktiv Rutoken lite 0`, прошивка 9.02, КриптоПро CSP 5.0 R2
(`C:\Program Files\Crypto Pro\CSP`). Это тот самый последний неисследованный путь из
[AGENTS.md](../../AGENTS.md) п. 21 и [ROADMAP.md](../../ROADMAP.md) P0 — «свой PC/SC-стек CSP на
уровне APDU».

## Главный вывод

**Файловый контейнер КриптоПро физически лежит в файловой памяти Рутокен Lite и полностью
читается по APDU.** КриптоПро CSP работает с Lite как с пассивной картой памяти: он сам вычитывает
`primary.key` (маскированный закрытый ключ), `masks.key` (маска+соль+CRC), `name.key` и сертификат
обычными командами `SELECT` / `READ BINARY` после `VERIFY PIN`, и сам же считает криптографию на
стороне хоста. Запрет на экспорт (`0x8009000b NTE_BAD_KEY_STATE`) — **программная проверка внутри
CSP**, она срабатывает в `CopyPrivateKey` уже **после** того, как ключевой материал прочитан с карты.

Это подтверждено двумя независимыми способами:

1. **Трасса самого CSP** — прокси-`winscard.dll` перехватил APDU, которыми `csptest -keycopy`
   читает контейнер, вплоть до отказа `0x8009000b`.
2. **Собственный съём** — маленькая утилита `litedump` **без КриптоПро** прочитала те же файлы
   контейнера (`primary.key`, `masks.key`, `primary2.key`, `masks2.key`, `name.key`) напрямую через
   PC/SC, использовав ровно ту же последовательность APDU.

То есть тезис README «на Lite проверенными способами не снимается» по части **чтения носителя**
опровергнут: маскированный закрытый ключ носитель отдаёт. Осталась только офлайн-арифметика снятия
маски — уже решённая в [ROADMAP.md](../../ROADMAP.md) §3.1 (см. «Что осталось» ниже).

## Метод: прокси-`winscard.dll`

`rutoken.dll` из состава CSP не импортирует WinSCard (AGENTS п. 21) — но импортирует его `pcsc.dll`
CSP (`SCardEstablishContext/Connect/Transmit/…`), а `cpscard.dll` ходит к карте через `pcsc.dll`.
Значит вся APDU-переписка Lite проходит через штатный `winscard.dll` Windows, и её можно перехватить
подстановкой прокси в каталог рядом с `csptest.exe`.

- Каталог CSP защищён от записи (нужна элевация), поэтому он **скопирован** в рабочую папку
  (59 файлов); контроль целостности КриптоПро сверяет хеши файлов, а не путь установки, — копия
  работает штатно (`enum_cont`/`keycopy` дают тот же результат).
- Прокси `winscard.dll` (x64, статический CRT) экспортирует **все 80 символов** реального
  `winscard.dll`: 77 функций форвардятся директивами `/export:Name=realscard.Name` на переименованную
  копию системного `winscard.dll` (`realscard.dll`), три структуры `g_rgSCard{Raw,T0,T1}Pci` отдаются
  своими статическими, а `SCardTransmit` и `SCardConnect{A,W}` перехвачены — логируют APDU/ответ,
  ридер и `hCard`, затем делегируют. Экспорт неполного набора даёт `0xC0000139` (ENTRYPOINT_NOT_FOUND),
  поэтому форвардится именно всё.
- Путь логирования задаётся переменной `APDU_LOG`.

Исходники и харнесс — в scratchpad сеанса (не в репозитории): `proxy_winscard.c`, `forwards.h`,
`run-apdu.ps1`, `litedump.c`.

## Протокол файлов контейнера на Lite

Файловая память Рутокена адресуется по абсолютному пути от MF. Наблюдаемые команды:

| Операция | APDU | Комментарий |
|----------|------|-------------|
| SELECT по пути | `00 A4 08 04 Lc  10 00 10 03 <DFhi DFlo> [<EFhi EFlo>] 00` | `1000`/`1003` — DF приложения КриптоПро; далее DF контейнера и EF файла |
| READ BINARY | `00 B0 <offHi> <offLo> <Le>` | `Le=00` → 256 байт |
| UPDATE BINARY | `00 D6 <offHi> <offLo> <Lc> <data>` | CSP пишет сюда при **ротации маски** (см. ниже) |
| VERIFY PIN | `00 20 00 02 <Lc> <PIN ASCII>` | P2=02 — пользовательский PIN; заводской `12345678` → `9000` |
| FCP файла | ответ `62 xx … 80 02 <size> 81 02 <alloc> 82 02 01 00 83 02 <FID> 8A 01 05 86 0F …` | тег `80` — число байт содержимого |

**Раскладка контейнера.** Каждый контейнер — отдельный DF `<idx>00` (в нашем случае `0B00`), а
шесть логических `*.key` — это EF `<idx>0N` внутри него. Соответствие установлено **по содержимому**
(ASN.1-грамматика из ROADMAP §3.1), а не по догадке:

| EF | Размер | Содержимое (ASN.1) | Логический файл |
|----|--------|--------------------|-----------------|
| `0B06` | 300 | `SEQ { IA5String(имя) }` (cp1251) | **name.key** |
| `0B03` | 2523 | большой `SEQ` с OID кривой `1.2.643.2.2.36.0` + вложенный X.509 | **header.key + сертификат** |
| `0B02` | 70 | `SEQ { OCTET STRING(32) }` | **primary.key** (обмен) |
| `0B01` | 60 | `SEQ { OCTET STRING(32), OCTET STRING(12), OCTET STRING(4) }` | **masks.key** (обмен) |
| `0B05` | 70 | `SEQ { OCTET STRING(32) }` | **primary2.key** (подпись) |
| `0B04` | 60 | `SEQ { OCTET STRING(32), OCTET STRING(12), OCTET STRING(4) }` | **masks2.key** (подпись) |

`SEQ{OS32}` = маскированный закрытый ключ; `SEQ{OS32,OS12,OS4}` = маска (32) + соль KDF (12) +
контрольная сумма (4) — те же поля, что у файлового контейнера в §3.1. Файлы дополнены до размера
FCP байтами `FF`.

## Что делает `csptest -keycopy` (трасса CSP)

Последовательность к Lite 0 (после сканирования соседних ридеров):

1. Перебор каталогов и `name.key` контейнеров (`SELECT … 0A06/0B06` → `READ BINARY` → имена в cp1251).
2. `80 40 00 00` (штатная преамбула) → `VERIFY PIN 12345678` → `9000`.
3. Чтение сертификата/заголовка (`0B03`) и **чтение `masks.key` (`0B01`) и `primary.key` (`0B02`)**
   командами `READ BINARY` — ключевой материал в открытом (маскированном) виде уходит с карты.
4. **`UPDATE BINARY` в `0B02` и `0B01`** — CSP переписывает `primary`/`masks` свежей маской (ротация;
   закрытый ключ `d = primary · mask⁻¹` при этом не меняется).
5. `CopyPrivateKey(AT_KEYEXCHANGE)` → **`0x8009000b`**. Экспорт запрещён — но пункт 3 уже произошёл.

Отказ приходит из `keycopy.c:331`, то есть из логики CSP, а не от карты: карта на все `READ BINARY`
отвечала `9000`.

## Независимый съём без CSP (`litedump`)

`litedump` подключается к `Aktiv Rutoken lite 0` напрямую через `winscard`, делает `VERIFY PIN` и
`READ BINARY` по EF `0B01…0B06`. Результат — все шесть файлов контейнера прочитаны, только чтение,
без единого обращения к КриптоПро:

```
connected proto=2
VERIFY PIN -> OK 9000
EF 0B01  size=60   read=60    masks.key  (обмен)    SEQ{OS32,OS12,OS4}
EF 0B02  size=70   read=70    primary.key(обмен)    SEQ{OS32}
EF 0B03  size=2523            header+сертификат      (личные данные — в отчёт не выносится)
EF 0B04  size=60   read=60    masks2.key (подпись)  SEQ{OS32,OS12,OS4}
EF 0B05  size=70   read=70    primary2.key(подпись) SEQ{OS32}
EF 0B06  size=300  read=300   name.key
```

Это и есть искомый CSP-free путь для Lite, аналог `RutokenExporter` (rtCOMLite) для Рутокен S —
только через штатный PC/SC APDU, а не через файловый API «Актива», который на Lite слеп (AGENTS п. 20).

## Что осталось — снятие маски (математика уже решена)

Из `primary.key` + `masks.key` закрытый ключ восстанавливается офлайн по процедуре
[ROADMAP.md](../../ROADMAP.md) §3.1:

1. ключ хранения = `CPKDF(пароль контейнера, соль из masks.key)` (Стрибог-256);
2. расшифровать `primary.key` алгоритмом ГОСТ 28147-89 (Магма) в ECB с узлом `id-tc26-gost-28147-param-Z`;
3. `d = (primary · mask⁻¹) mod q`, где `q` — порядок группы кривой из заголовка (`1.2.643.2.2.36.0` = CryptoPro-XchA);
4. оракул проверки — `d·G == Q`, где `Q` — открытый ключ из сертификата (лежит в `0B03`).

Эта арифметика в §3.1 **уже доведена до совпадения** на трёх файловых контейнерах владельца той же
грамматики. В этом сеансе прямой перенос **до `d·G == Q` не доведён**: собственная реализация 28147/CPKDF
на `gostcrypto` не сошлась перебором 256 комбинаций осей (порядок строк S-box, порядок слов/байт,
пустой пароль vs PIN, формула) — это ровно «грабли точных конвенций КриптоПро», описанные в §3.1.
Проверено, что `Q` из сертификата **лежит на кривой CryptoPro-A** (`q·G = O`), то есть параметры и
разбор публичного ключа верны — расходится именно шаг расшифрования `primary.key`.

Правильный следующий шаг — не переписывать примитивы заново, а взять **валидированную реализацию из
§3.1** (BouncyCastle: Param-Z строками в обратном порядке, дайджест Стрибога без разворота) и подать ей
на вход EF `0B01/0B02`, прочитанные `litedump`. Единственная новая проверка перед байтовым `d·G == Q` —
пуст ли у токенных контейнеров «пароль контейнера» для CPKDF (у файловых, на которых §3.1 сошёлся, он
пуст); PIN `12345678` в §3.1 в KDF не участвовал.

## Значение для проекта

- **Lite (файловый контейнер) снимается по APDU.** Носитель отдаёт маскированный закрытый ключ и
  маску; «неэкспортируемость» на Lite — софтверный флаг CSP, а не свойство чипа (в отличие от
  Рутокен ЭЦП, где ключ аппаратно неизвлекаем, AGENTS п. 26).
- Практический путь для `Core`: `RutokenLiteApdu` (PC/SC `SCardTransmit`, тот же протокол, что в
  `litedump`) → файлы контейнера → офлайн-разбор §3.1 → PKCS#8/PFX. Ни rtCOMLite, ни запрет на
  экспорт, ни `p12utility --cprepair` при этом не нужны.
- Формулировку в README для Lite после доведения §3.1 до `d·G == Q` можно менять с «проверенными
  способами не снимается» на «снимается по APDU + офлайн-разбор». **До байтовой проверки** корректно
  писать: «ключевой материал читается по APDU мимо CSP; снятие маски — по §3.1».

## Воспроизведение

Оснастка сеанса — в scratchpad (локально, не в репозитории, содержит персданные владельца):

```
proxy_winscard.c / forwards.h   прокси-winscard.dll (сборка: cl /LD /MT, экспорт через /export-pragma)
run-apdu.ps1                    деплой прокси в копию CSP + enum/check/keycopy с логом APDU
litedump.c                      независимый съём EF контейнера через PC/SC (только чтение)
reconstruct2.py                 попытка снятия маски (не сошлась; переиспользовать §3.1)
logs/*.apdu.log                 трассы APDU (содержат сертификат и PIN — локально)
```

Сборка прокси и снятие:

```powershell
# из каталога с исходниками (нужен MSVC x64 + Windows SDK):
cl /nologo /LD /O2 /MT proxy_winscard.c /Fe:winscard.dll user32.lib   # прокси
cl /nologo /O2   /MT litedump.c        /Fe:litedump.exe  winscard.lib  # ридер
```

**Обязательный preflight по PIN — не пропускать.** `litedump` делает `VERIFY PIN`, а у Рутокена
счётчик попыток: слепой ввод `12345678` на токене с изменённым PIN **тратит попытку и при повторах
блокирует токен**. Поэтому PIN не подбирают — сперва проверяют его дефолтность **без единой попытки
входа** по флагу `CKF_USER_PIN_TO_BE_CHANGED` (PKCS#11 `CK_TOKEN_INFO`, в проекте — `Pkcs11Token`,
AGENTS п. 21), заодно смотрят, что счётчик чист (`UserPinCountLow`/`UserPinFinalTry`/`UserPinLocked`).
`litedump` запускают **только если дефолтность подтверждена**; если PIN не заводской — берут верный у
владельца и подставляют его, а не значение из примера. При PIN, отличном от 8 символов, поправить
`Lc` в `VERIFY` (`00 20 00 02 <Lc> …`).

```powershell
CryptoProExport.exe token           # покажет состояние PIN (дефолтный / счётчик) без траты попыток
# только при подтверждённой дефолтности:
litedump.exe "Aktiv Rutoken lite 0" 0B00 12345678 dump                 # съём EF (только чтение)
```

## Оговорки

- **Персональные данные.** EF `0B03` — реальный сертификат владельца (ФНС), `primary/masks` — его
  маскированный закрытый ключ. Сырые дампы и логи остаются локально; в этот отчёт байты ключа, маски
  и содержимое сертификата не вынесены.
- **Ротация маски.** `csptest -keycopy` перезаписал `primary`/`masks` целевого контейнера свежей
  маской (`UPDATE BINARY`). Это штатное поведение CSP при доступе к ключу и контейнер не портит:
  `d = primary · mask⁻¹` инвариантно. `litedump` ничего не пишет.
- **PIN.** Заводской `12345678` подтверждён успешным `VERIFY` самого CSP (счётчик не тратится при
  верном PIN). Проверять дефолтность до ввода — по `CKF_USER_PIN_TO_BE_CHANGED` (AGENTS п. 21).
- **Состояние токена.** После сеанса на Lite 0 те же три контейнера, что и до него.
- **Разрядность.** Прокси и `litedump` собраны x64 под `csptest.exe` x64 из `C:\Program Files\Crypto Pro\CSP`.
