# JaCarta LT (VID_24DC/PID_0102): прямой APDU-экспорт

Этот документ относится только к JaCarta LT с USB `VID_24DC/PID_0102`, проверенной
26.08.2026 и повторно 27.08.2026. Серийный номер и постоянные пользовательские данные
здесь не сохраняются. Проверенный PC/SC reader в Unified Client 3.3 —
`Aladdin R.D. JaCarta LT 0`; прежний драйвер показывал `ARDS ZAO JaCarta LT 0`.

## Итог

JaCarta LT — поддерживаемый пассивный носитель. `CryptoProExport` распознаёт модель
PKCS#11 `JaCarta DS` / апплет Datastore, безопасно перечисляет контейнеры без PIN,
а после явной авторизации читает шесть файлов контейнера КриптоПро напрямую по
PC/SC APDU. Ни PKCS#11-объекты, ни jcFS для контейнера CSP не требуются.

Production-путь реализован в `JaCartaLtApdu`, общий точный маршрутизатор —
`DirectTokenApdu`. Команды:

```text
tokenexport <reader> <outDir> [pin]  — сохранить исходные шесть файлов
tokenfull   <reader> <outDir> [pin]  — дополнительно найти .cer и снять запрет
```

Протокол чтения не записывает данные на токен. Неподходящий тип носителя до APDU
отсекается по положительной классификации PKCS#11/reader; путь Рутокен Lite или
Маршрут eToken PRO/PRO для LT не используется.

## Точная идентификация

| Уровень | Проверенное значение |
|---|---|
| USB | `VID_24DC`, `PID_0102`, CCID |
| PC/SC | `Aladdin R.D. JaCarta LT 0` (`ARDS ZAO…` в прежнем драйвере), T=1 |
| PKCS#11 | `jcPKCS11-2.dll`, model `JaCarta DS` |
| Апплет | Datastore, AID `A000000448000301` |
| Назначение | пассивный носитель контейнеров программного СКЗИ |

JaCarta LT не является проверенным eToken PRO/PRO: у PRO другой PKCS#11 model и
другой апплет. Отдельный брендированный JaCarta PRO также нельзя отождествлять с
этими устройствами по одному названию апплета.
Переносить команды между ними только по торговой марке нельзя.

## Проверенный APDU-протокол

Протокол восстановлен трассировкой точного вызова КриптоПро CSP и затем подтверждён
самостоятельным read-only пробником до байта:

1. Выбрать Datastore:
   `00 A4 04 00 08 A0 00 00 04 48 00 03 01`.
2. Читать таблицу объектов страницами:
   `80 20 60 00 02 <offset-BE> 00`. Одна запись занимает 7 байт.
3. Для защищённых объектов выполнить один вход:
   `80 10 10 00 <Lc> 00 <pin-length> <pin-ascii>`.
4. Читать объект:
   `80 20 30 00 06 00 <index> <offset-BE> <length-BE> 00`.

Коды объектов контейнера:

| Код | Файл |
|---|---|
| `F6` | `name.key` |
| `F3` | `header.key` |
| `F2` | `primary.key` |
| `F1` | `masks.key` |
| `F5` | `primary2.key` |
| `F4` | `masks2.key` |

Перед сохранением production-код требует `name.key`, `header.key` и хотя бы одну
полную пару `primary*.key` + `masks*.key`; половина пары считается повреждением и
блокирует результат.

## Физический E2E 26–27.08.2026

На точном LT был создан отдельный синтетический двухключевой контейнер КриптоПро.
До чтения оба ключа были неэкспортируемыми:

- обмен: `KP_PERMISSIONS=0x00130898`;
- подпись: `KP_PERMISSIONS=0x00122898`;
- в обоих значениях отсутствовал `CRYPT_EXPORT=0x4`.

PKCS#11 после корректного входа показывал 0 объектов, jcFS не показывал контейнер
CSP. Новый APDU-бэкенд прочитал полный набор: `name.key` 14 байт,
`header.key` 1263 байта после помещения сертификатов, обе `primary` по 70 байт и
обе `masks` по 56 байт.

Затем публичная команда `tokenfull`:

- извлекла обменный и подписной сертификаты через CryptoAPI;
- успешно выполнила `p12utility --cprepair --keyexport --keyexport_sg`;
- установила переименованную копию точно в `HDIMAGE`;
- получила `0x0013089C` и `0x0012289C`, то есть `CRYPT_EXPORT` у обеих пар;
- выгрузила обменный PFX через штатный `certmgr`; файл принят `certutil -dump`.

После проверки синтетический контейнер, HDIMAGE-копия, сертификаты и PFX удаляются.
Другие носители, включая подключённый Рутокен ЭЦП, в записывающих командах не
используются.

### Независимый повтор 27.08.2026

Расходный LT был заново отформатирован в Unified Client 3.3.5.3866. Общий и отдельный
STORAGE PKCS#11-модули честно возвращают `CKR_FUNCTION_NOT_SUPPORTED` на `C_InitPIN`;
штатный для Datastore вызов `C_SetPIN` с действующим административным PIN установил
новый пользовательский PIN, после чего реальный `CKU_USER`-login прошёл с чистыми
счётчиками. Случайные значения PIN после этого не проверялись.

На свежем двухключевом контейнере production `tokenfull` прочитал `name.key` 13 байт,
`header.key` 1257 байт, обе `primary` по 70 байт и обе `masks` по 56 байт. Затем:

- `p12utility --cprepair --keyexport --keyexport_sg` — код 0;
- HDIMAGE-копия видна CSP;
- обмен `0x0013089C`, подпись `0x0012289C`;
- `topfx` подтвердил ссылку сертификата на контейнер и создал PFX;
- OpenSSL увидел MAC, `Shrouded Keybag` и `Certificate bag`.

Это свежий полный прогон на текущем драйвере, а не повторное использование артефактов
проверки 26.08.

## Безопасность PIN

PIN не подбирается. Явно введённое значение используется один раз. Заводское значение
может быть выбрано автоматически только если PKCS#11 одновременно подтверждает чистое
состояние `UserPinToBeChanged` и отсутствие `CountLow`, `FinalTry` и `Locked`.
При любом сомнительном флаге команда останавливается до APDU LOGIN.
