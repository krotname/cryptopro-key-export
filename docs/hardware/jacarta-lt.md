# JaCarta LT (VID_24DC/PID_0102): проверенная граница поддержки

Этот документ относится только к экземпляру JaCarta LT, проверенному 21.08.2026
через PC/SC-считыватель `Aladdin R.D. JaCarta LT 0`. Здесь намеренно нет серийного
номера, полного PnP Device ID, PIN-кодов, имён контейнеров и сертификатов.

## Что поддерживает CryptoProExport

- PKCS#11-модель `JaCarta DS` и связка `Datastore` + `Aladdin R.D.` распознаются
  как отдельный тип `JaCarta LT`, а не как безликий «токен другого вендора».
- GUI и CLI показывают название `JaCarta LT` и безопасно читают доступные без
  авторизации метаданные PKCS#11.
- Этот тип исключён из файлового обхода `rtCOMLite`: API Рутокена S к JaCarta
  неприменимо, а вызовы нативного файлового API на неподходящем носителе опасны.
- Путь `RutokenLiteApdu` по-прежнему запускается только для `RutokenLite`.
  JaCarta LT к нему не подключается и APDU-протокол JaCarta PRO не наследует.
- Экспортного действия для JaCarta LT пока нет. Наличие носителя в списке —
  диагностика, а не заявление о возможности снять закрытый ключ.

## Точная идентификация проверенного носителя

| Уровень | Проверенное значение |
|---|---|
| USB | `VID_24DC`, `PID_0102`; устройство CCID, состояние PnP `OK` |
| PC/SC | `Aladdin R.D. JaCarta LT 0`, протокол T=1 |
| ATR | `3B DC 18 FF 81 91 FE 1F C3 80 73 C8 21 13 66 01 06 11 59 00 01 28` |
| Windows | Microsoft USB CCID; установлен minidriver `jclasermd` |
| Клиент | JaCarta Unified Client 3.1.2.3478 |
| PKCS#11 | `jcPKCS11-2.dll` x86/x64, версия 2.9.0.874, подпись Aladdin R.D. действительна |
| jcFS | `jcFS.dll` x86/x64, версия 1.2.0.135 |

Официальная карточка называет JaCarta LT носителем контейнеров **программных**
СКЗИ и указывает 102 Кбайт EEPROM, Microsoft CCID и PKCS #11. Отдельная публикация
«Аладдин Р.Д.» прямо относит JaCarta LT к пассивным ключевым носителям. Это
согласуется с назначением устройства, но само по себе не доказывает формат файлов
или возможность извлечения конкретного контейнера.

## Read-only результаты

### PKCS#11

Обе разрядности `jcPKCS11-2.dll` дали одинаковый результат без `C_Login`:

- Cryptoki 2.40, производитель `Aladdin R.D.`, библиотека 2.09;
- один слот, сопоставленный с точным PC/SC-считывателем; числовой slot ID не
  используется как стабильный идентификатор;
- label `Default`, model `JaCarta DS`, firmware 1.02, hardware 1.0;
- длина PIN 6–32, `LoginRequired=true`, `UserPinInitialized=true`,
  `WriteProtected=false`, `ProtectedAuthenticationPath=false`;
- флаги `UserPinToBeChanged`, `CountLow`, `FinalTry`, `Locked` и соответствующие
  SO-флаги не установлены;
- механизмов 0, публично видимых объектов 0.

Ноль объектов без входа не доказывает пустую файловую систему Datastore: защищённые
объекты могут стать видимы только после авторизации. `C_Login` не выполнялся,
неизвестный PIN и опубликованный заводской PIN не проверялись, попытки не расходовались.

### jcFS

Через x64 `jcFS.dll` выполнены только безопасные операции:

- `JCTokenBind` успешно привязал точное имя считывателя;
- `JCSelectApplet(0x2205)` успешно выбрал Datastore;
- прочитаны model `JC290-16 v4.2`, label `Default` и полный счётчик из 10
  оставшихся PIN-попыток; идентификатор токена не сохранялся, проверялся только его hash.

`JCRootDirOpen` намеренно не вызывался. Официальная документация предупреждает:
если корневой директории нет, функция создаст её, поэтому перед ней требуется
`JCTokenLogin`. До появления проверенного PIN и отдельной необходимости такой вызов
не является read-only.

### APDU и CryptoPro CSP

- SELECT AID JaCarta PRO CryptoPro `A0000003120202` вернул `6E00`: PRO-апплет
  на этом LT отсутствует.
- SELECT AID Datastore `A000000448000301` вернул `9000`.
- `csptest -card` x86 увидел точный считыватель и тот же ATR.
- `csptest -keyset -enum_cont -fqcn -verifycontext` для provider type 75, 80 и
  81 завершился кодом 0; на точном LT контейнеров не было.

Успешный SELECT Datastore подтверждает апплет, но не раскрывает протокол каталогов.
Нулевой список CSP подтверждает только состояние этого экземпляра в момент проверки.

## Почему это не JaCarta PRO

| Признак | JaCarta LT из этого сеанса | Ранее исследованная JaCarta PRO |
|---|---|---|
| PKCS#11 model | `JaCarta DS` | `PRO` |
| Апплет | Datastore | PRO / CryptoPro |
| AID Datastore | принят (`9000`) | не основание для PRO-выводов |
| AID PRO CryptoPro | отвергнут (`6E00`) | использовался в PRO-исследовании |
| Допустимый вывод | отдельная диагностика LT | описан только в [jacarta-pro.md](../apdu/jacarta-pro.md) |

Файловую раскладку, команды APDU, KDF и выводы об извлекаемости из PRO нельзя
переносить на LT по торговой марке: аппаратно подтверждены разные апплеты.

## Доказательная граница

На проверенном LT не было контейнеров CSP, а PIN неизвестен. Поэтому пока не доказаны:

- безопасное перечисление каталогов/файлов Datastore после авторизации;
- соответствие данных Datastore шести файлам контейнера КриптоПро;
- чтение собственного неэкспортируемого контейнера и восстановление того же ключа;
- экспорт PFX без штатного разрешения CSP.

До такого опыта приложение не должно предлагать LT-экспорт, пробовать PIN, открывать
корень jcFS или выполнять PRO/Rutoken Lite APDU. Корректный текущий результат — точное
распознавание и честная диагностика.

## Безопасный протокол будущего синтетического теста

Этот протокол **не выполнялся**. Он нужен только если владелец предоставит проверенный
PIN именно этого LT и read-only диагностики будет недостаточно.

1. Повторно идентифицировать `VID_24DC/PID_0102` и точный PC/SC reader; другие
   подключённые носители исключить из команд по имени считывателя.
2. Снять обезличенный baseline: PKCS#11 flags, jcFS-счётчик попыток и CSP-контейнеры
   точного LT. Остановиться при `CountLow`, `FinalTry`, `Locked` или расхождении модели.
3. Использовать только заранее проверенный владельцем PIN LT; не пробовать PIN от PRO
   и не угадывать заводское значение.
4. Выбрать уникальное нейтральное имя `cpxlt-<случайный суффикс>` и доказать его
   отсутствие на LT, в HDIMAGE и в хранилище сертификатов до записи.
5. Создать на LT ровно один синтетический контейнер КриптоПро и самоподписанный
   сертификат; проверить, что `KP_PERMISSIONS` не содержит `CRYPT_EXPORT`.
6. После успешного входа использовать документированный jcFS backend. Открывать корень
   только теперь, когда CSP уже создал данные и создание пустого root не подменит опыт.
7. Перечислить и читать только дерево нового контейнера; не использовать PRO APDU и не
   делать предположений о формате до проверки каждого файла.
8. Сверить извлечённый открытый ключ/сертификат и только затем проверять восстановление
   закрытого ключа в изолированной выходной папке.
9. Удалить только синтетический контейнер и его сертификат, затем повторить baseline и
   подтвердить отсутствие изменений остальных носителей и контейнеров.
