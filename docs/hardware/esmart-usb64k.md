# ESMART Token USB 64K и ESMART Token: полный аппаратный E2E

Проверено 27.08.2026 на двух собственных расходных носителях. Оба были
инициализированы заново, поэтому тест включал записывающие операции, генерацию ключей,
создание контейнеров и итоговую очистку. Полные серийные номера, PIN и ключевой материал
в репозитории не сохраняются.

## Итог

Файловый контейнер КриптоПро на обоих ESMART поддерживается production-кодом.
`CryptoProExport` строго подтверждает семейство через системный PKCS#11-модуль ISBC,
находит контейнеры в пассивном CSP-разделе, читает шесть файлов по PC/SC APDU и
проводит полный цикл до экспортируемой HDIMAGE-копии и PFX.

Это не означает, что любой ключ ESMART извлекаем. Отдельно сгенерированная через
PKCS#11 аппаратная RSA-пара осталась `CKA_NEVER_EXTRACTABLE=true`; утилита снимает
именно файловый контейнер программного КриптоПро CSP.

## Точные устройства и окружение

| Устройство | USB | PC/SC | Протокол |
|---|---|---|---|
| ESMART Token USB 64K | `VID_072F/PID_90DE` | `ESMART Token USB 64K 0` | T=0 |
| ESMART Token | `VID_2CE4/PID_7479` | `ISBC ESMART Token 0` | T=0 |

На Windows установлен ESMART PKI Client 4.17.4. Проверены обе системные пары DLL:

- `isbc_pkcs11_main.dll` — точка входа;
- `isbc_esmart_token_mod.dll` — обязательный backend рядом с ней;
- x64-пара используется 64-битной диагностикой, x86-пара — portable-сборкой проекта.

Приложение не вшивает эти DLL и не подбирает случайные копии из сторонних программ.
Модуль ESMART считается доступным, только когда найдена архитектурно подходящая полная
пара из штатного каталога.

## PKCS#11: что проверено

Оба носителя были форматированы и получили новые пользовательские PIN. На каждом
выполнены одни и те же проверки:

1. Создание публичного и закрытого data-object и сертификата, видимость до/после
   `C_Login`, затем полное удаление объектов.
2. Генерация RSA-2048, подпись и проверка подписи — успешно.
3. Закрытый ключ: `CKA_EXTRACTABLE=false`, `CKA_SENSITIVE=true`,
   `CKA_ALWAYS_SENSITIVE=true`, `CKA_NEVER_EXTRACTABLE=true`, `CKA_LOCAL=true`;
   чтение `CKA_VALUE` запрещено.
4. `C_WrapKey` не дал копию ключа (`CKR_WRAPPING_KEY_TYPE_INCONSISTENT`), импорт
   тестового AES-ключа отклонён (`CKR_ATTRIBUTE_VALUE_INVALID`).
5. Генерация ГОСТ-пары универсальным PKCS#11-механизмом отклонена
   (`CKR_MECHANISM_INVALID`). Это согласуется с архитектурой ESMART: ГОСТ-контейнер
   обслуживает программный CSP, а не универсальный аппаратный PKCS#11-объект.

После теста список объектов на обоих носителях снова был пуст.

## Файловый контейнер CSP: полный цикл

На каждом ESMART КриптоПро CSP создал отдельный синтетический контейнер с ключами
обмена и подписи и двумя самоподписанными тестовыми сертификатами. Исходные ключи
были неэкспортируемыми; штатное `csptest -keycopy` токен→HDIMAGE на обоих устройствах
завершилось `0x8009000B`.

Production-команда `tokenfull` на каждом устройстве прочитала:

| Файл | Размер |
|---|---:|
| `name.key` | 13 байт |
| `header.key` | 1257 байт |
| `primary.key` / `primary2.key` | по 70 байт |
| `masks.key` / `masks2.key` | по 56 байт |

Далее для каждого контейнера независимо подтверждено:

- `p12utility --cprepair --keyexport --keyexport_sg` завершился успешно;
- точная HDIMAGE-копия стала видна КриптоПро;
- обмен: `KP_PERMISSIONS=0x0013089C`;
- подпись: `KP_PERMISSIONS=0x0012289C`;
- `topfx` связал сертификат с ключом и создал PFX;
- OpenSSL увидел MAC, `Shrouded Keybag` и `Certificate bag`.

Таким образом, оба ESMART прошли не частичную диагностику, а полный путь
«неэкспортируемый контейнер на носителе → шесть файлов → снятие запрета → CSP → PFX».

## Production APDU-протокол

Протокол восстановлен по трассе штатного ESMART/CSP и повторён независимым
read-only backend `EsmartApdu`:

1. `SELECT MF`, затем `SELECT DF 7F01`.
2. Контейнерные слоты: `F100`…`F900`.
3. Для слота `Fx00` используются EF:

| Суффикс | Файл |
|---|---|
| `06` | `name.key` |
| `03` | `header.key` |
| `02` / `01` | `primary.key` / `masks.key` |
| `12` / `11` | `primary2.key` / `masks2.key` |

4. Размер берётся из FCP tag `80` в big-endian.
5. PIN проверяется стандартной `VERIFY` для reference `81`.
6. EF читается только `READ BINARY` блоками до 255 байт.
7. Фиксированный EF начинается служебным байтом `01`, далее идёт DER и нулевой хвост;
   backend снимает маркер только при точной последовательности `01 30` и ограничивает
   результат объявленной DER-длиной.

Команд записи, удаления или форматирования `EsmartApdu` не содержит. Перед первой APDU
маршрутизатор требует одновременно `Kind=Esmart`, вендорское свидетельство ISBC/ESMART
из PKCS#11 и согласованное семейство model/reader; совпадения одной строки reader
недостаточно.

## Границы и что требует внимания

- Физически подтверждены только две строки USB/reader из таблицы выше. Другой ESMART
  нельзя автоматически считать совместимым только по торговой марке.
- Аппаратные PKCS#11-ключи не становятся файловыми контейнерами и этим backend не
  экспортируются.
- Для работы нужна полная системная пара DLL правильной разрядности.
- На устройстве `VID_2CE4/PID_7479` прежний Code 10 оказался временным сбоем PnP-start;
  актуальный readback — `Status=OK`, `ProblemCode=0`. История диагностики сохранена в
  [esmart-token-code10.md](esmart-token-code10.md).
