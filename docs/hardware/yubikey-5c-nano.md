# YubiKey 5C Nano — не носитель КриптоПро (проверено 07.09.2026)

Сеанс на живом экземпляре 07.09.2026 по [runbook token-e2e](../runbooks/token-e2e.md).
Итог короткий: **E2E из runbook на этом устройстве не стартует и не может стартовать** —
КриптоПро не создаёт на нём контейнер, потому что карта не является носителем CSP ни при
каких драйверах. Отдельно проверен PKI-путь самого YubiKey (апплет PIV): ключ генерируется
и подписывает на чипе, наружу выходит только открытая часть.

Данные обезличены: приведены только признаки самого расходного устройства.

## Точная идентификация

| Признак | Значение |
|---|---|
| Считыватель (PC/SC) | `Yubico YubiKey OTP+FIDO+CCID 0` |
| USB | составное `VID_1050&PID_0407`: `MI_00` HID/OTP, `MI_01` FIDO HID, `MI_02` CCID |
| Драйвер считывателя | штатный Windows «Устройство чтения смарт-карт Microsoft Usbccid (WUDF)» |
| Карта в Windows | `Устройство идентификации (NIST SP800-73 [PIV])`, `SCFILTER\CID_8073C021C057597562694B6579` |
| ATR | `3B FD 13 00 00 81 31 FE 15 80 73 C0 21 C0 57 59 75 62 69 4B 65 79 40` (исторические байты — ASCII `YubiKey`) |
| Модель (`ykman info`) | YubiKey 5C Nano, форм-фактор Nano (USB-C) |
| Серийный номер | `23054120` |
| Прошивка | `5.4.3` (подтверждена и по APDU апплетом управления: `Virtual mgr - FW version 5.4.3`) |
| Апплеты | Yubico OTP, FIDO U2F, FIDO2, OATH, PIV, OpenPGP, YubiHSM Auth — все Enabled |
| Заводские секреты PIV | PIN `123456`, PUK `12345678`, management key TDES `0102…0708` (все три были заводские) |

**Не путать** с Yubico Security Key (серия FIDO-only): у неё нет CCID-интерфейса и апплета
PIV вовсе, поэтому в PC/SC она не появляется и разговор о носителе не возникает.

## Почему это не носитель КриптоПро (четыре независимых доказательства)

### 1. ATR не совпал ни с одной записью карт-модулей CSP

`HKLM\SOFTWARE\WOW6432Node\Crypto Pro\Cryptography\CurrentVersion\KeyCarriers` — 51 носитель,
**83 записи с ATR/ATRMask**; сверка живого ATR по маске: 0 совпадений. В `Calais` Windows
записи с этим ATR тоже нет: карту берут `Identity Device (NIST SP 800-73 [PIV])` и
`Identity Device (Microsoft Generic Profile)`, а у них поля `ATR` нет вообще — они
подбираются по AID, а не по ATR.

### 2. Диалог CSP при попытке создать контейнер

```powershell
pwsh token-session\make-token-container.ps1 `
  -ContainerPath "\\.\Yubico YubiKey OTP+FIDO+CCID 0\cpxt_yknano" -Password 123456
```

КриптоПро показывает «Выбор ключевого носителя», где считыватель стоит в группе
**«Недоступные для данной операции»** с описанием
**«Смарт-карта не читается в устройстве чтения из-за конфликтов настройки ATR»**;
харнесс закрывает диалог, `csptest` выходит с `0x8010006E` (`SCARD_W_CANCELLED_BY_USER`).

> **Грабли: формулировка про «конфликты настройки ATR» вводит в заблуждение.** Никакого
> конфликта нет — ATR не заявляет **ни один** карт-модуль (см. п. 1). Это дежурный текст CSP
> для «ATR не опознан». Не искать по нему драйвер: вендорского драйвера, добавляющего
> КриптоПро карт-модуль для YubiKey, не существует, а CCID-часть и без того уже обслужена
> штатным Windows-драйвером.

### 3. Тот же отказ без единого диалога

Прямой вызов CryptoAPI мимо UI (`CRYPT_SILENT`) даёт чистый код:

| Вызов | Флаги | Код |
|---|---|---|
| `CryptAcquireContext("\\.\Yubico YubiKey OTP+FIDO+CCID 0\cpxt_yknano", "Crypto-Pro GOST R 34.10-2012 KC1 CSP", 80, …)` | `CRYPT_NEWKEYSET` + `CRYPT_SILENT` | `0x80090019` `NTE_KEYSET_NOT_DEF` |
| то же | `CRYPT_SILENT` | `0x80090019` |

`enum_cont` до и после сеанса печатает те же четыре HDIMAGE-контейнера — носителя CSP на
YubiKey не появляется ни при какой операции.

### 4. Контейнеру негде лежать физически

Прямые APDU через PC/SC (shared, T=1):

| Проба | Ответ | Смысл |
|---|---|---|
| `00 A4 00 00 02 3F 00` (SELECT MF) | `6D 00` | **ISO-файловой системы нет** — шести `*.key` разместить негде |
| `00 A4 04 00 05 A0 00 00 01 01 00` | `6A 82` | посторонний DF не найден |
| SELECT `A0 00 00 03 08` (PIV) | `61 11 4F 06 00 00 10 00 01 00 79 07 4F 05 A0 00 00 03 08 90 00` | апплет PIV, версия `00 00 10 00 01 00` |
| SELECT `D2 76 00 01 24 01` (OpenPGP) | `90 00` | апплет OpenPGP есть |
| SELECT `A0 00 00 05 27 21 01` (OATH) | `79 03 05 04 03 … 90 00` | апплет OATH, версия `5.4.3` |
| SELECT `A0 00 00 05 27 47 11 17` (mgmt) | `Virtual mgr - FW version 5.4.3` `90 00` | апплет управления |
| SELECT `A0 00 00 06 47 2F 00 01` (U2F) | ошибка транспорта `0x80100027` | FIDO живёт на HID-интерфейсе, не на CCID |

Ни ГОСТ-механизмов, ни файловой памяти под контейнер КриптоПро у устройства нет: PIV и
OpenPGP YubiKey 5 работают с RSA и NIST-кривыми.

## Свой PKI-путь YubiKey: ключ на чипе и неизвлекаем

Проверено конструктивно на расходном устройстве при **всех трёх заводских секретах на руках**
(PIN, PUK, management key) — то есть с максимальными правами, какие вообще бывают у владельца:

1. `ykman piv keys generate --algorithm ECCP256 --pin-policy ONCE --touch-policy NEVER 9a pub.pem`
   → ключ создан **на карте**, `ykman piv keys info 9a` показывает `Origin: GENERATED`.
2. `ykman piv keys attest 9a` → аттестационный сертификат `CN=YubiKey PIV Attestation 9a`,
   подписанный ключом устройства `CN=Yubico PIV Attestation` (слот `F9`), тот в свою очередь
   выпущен `CN=Yubico PIV Root CA Serial 263751`. `openssl verify -partial_chain -CAfile <F9>`
   → `OK`. Расширения Yubico в аттестации подтверждают ровно тот экземпляр:

   | OID | HEX | Значение |
   |---|---|---|
   | `1.3.6.1.4.1.41482.3.3` | `05 04 03` | прошивка 5.4.3 |
   | `1.3.6.1.4.1.41482.3.7` | `02 04 01 5F C7 28` | серийный `23054120` |
   | `1.3.6.1.4.1.41482.3.8` | `02 01` | PIN policy ONCE, touch policy NEVER |
   | `1.3.6.1.4.1.41482.3.9` | `04` | форм-фактор USB-C Nano |

3. `ykman piv certificates generate --subject "CN=cpxt_yknano" 9a pub.pem` → самоподписанный
   сертификат; подпись `ecdsa-with-SHA256` посчитал **сам токен** (у ykman есть только открытый
   ключ). `openssl verify -CAfile cert9a.pem cert9a.pem` → `OK`: ключ живой и рабочий.
4. `ykman piv keys export 9a` отдаёт **открытый** ключ («export a public key corresponding to a
   stored private key»). SHA-256 DER-формы совпадает у трёх источников — вывода генерации,
   «экспорта» и `SubjectPublicKeyInfo` сертификата слота: наружу выходит только открытая часть.
5. Команды чтения закрытого ключа в NIST SP 800-73 нет вовсе: `GENERAL AUTHENTICATE` умеет
   только подпись и согласование ключа, а `GET DATA` адресует объекты данных (сертификаты,
   CHUID), а не ключевые слоты.

Итог PKI-пути: **резервная копия закрытого ключа невозможна по конструкции** — как у Рутокен
ЭЦП и JaCarta-2 ГОСТ, но по другой причине: там активный ГОСТ-апплет, здесь — чужой стандарт.

## Поведение утилиты (fail-closed, проверено)

```
[PC/SC]   Yubico YubiKey OTP+FIDO+CCID 0 [YubiKey (PIV/FIDO)] — карта вставлена, ATR 3B FD 13 …
  Такая карта не является PKCS#11-токеном; если это и не носитель КриптоПро, экспортировать нечего.
```

- `list` не падает и не выдумывает бэкенд: ни одна установленная библиотека PKCS#11 карту не
  показывает (`Найдено устройств: 0` у всех), `rtCOMLite` — 0 устройств.
- `checkexport "\\.\Yubico YubiKey OTP+FIDO+CCID 0\cpxt_yknano"` → код 2 и точное сообщение
  «Контейнер … не найден», а не ложный успех.
- До 07.09.2026 строка звучала как «неизвестный носитель»; теперь `PcscReaders.CarrierHintKey`
  называет вендора (`carrier.yubikey`), чтобы владелец не искал несуществующий драйвер.

## Второй экземпляр линейки и запасной признак по ATR (07.09.2026)

Владелец подключил к телефону второй ключ Yubico — `1050:0402`, USB `product` `YubiKey FIDO`,
**единственный** интерфейс класса `03` (HID). Смарт-карты в нём нет вовсе, поэтому в PC/SC
Windows такой экземпляр и не появится: PC/SC-считыватель создаёт именно CCID-интерфейс, а его
здесь нет. Отдельной ветки под него на Windows не требуется (в Android-порту потребовалась —
там устройство доходит до USB-транспорта и падает в нём, см. `krotname/cryptopro-key-export-android` PR #47).

Что на Windows всё же оказалось неполным: `CarrierHintKey` смотрел **только на имя считывателя**.
Прямое подключение оно закрывает (`Yubico YubiKey OTP+FIDO+CCID 0`), а вот ключ, вставленный в
универсальный CCID-считыватель, снова стал бы «неизвестным носителем» — имя там принадлежит
ридеру, а не карте. Тот же случай уже известен по ESMART Token ГОСТ в `Feitian SCR301`.

Добавлена перегрузка `CarrierHintKey(readerName, atrHex)`: сначала имя, и **только** на
`carrier.unknown` смотрим печатные historical bytes ATR — у YubiKey там ASCII `YubiKey`. Порядок
именно такой, чтобы у уже распознаваемых вендоров поведение не менялось ни в одном случае.
Живьём этот путь не снят: универсального считывателя в сеансе не было, ветка закрыта тестом на
живом ATR.

**В реестр заводских PIN (`StandardPins`) устройство намеренно не внесено.** У записи Windows-реестра
нет признака «поддержки не будет», и `Supported = false` отрисовалось бы как «в плане» — обещание,
которого не будет. Тот же порядок уже действует для iBank 2 Key: он в реестре тоже отсутствует.
В Android-порту запись есть, потому что там у модели есть отдельный флаг `exportPossible`.

## Уборка и приёмка

`ykman piv reset` вернул апплет PIV к заводскому состоянию: слот `9A` пуст
(`No key stored in slot 9A`), CHUID и CCC снова отсутствуют, PIN/PUK/management key заводские —
ровно то состояние, в котором устройство было принято. `enum_cont` совпал с baseline,
сертификата `CN=cpxt_yknano` в «Личном» не появлялось ни разу (минидрайвер PIV его не
публиковал), рабочая папка удалена.

## Итог для кода

Бэкенд не пишется и маршрутизация не добавляется: снимать нечего — контейнера КриптоПро на
этом устройстве не существует. Единственное изменение — честное имя носителя в диагностике
PC/SC. Устройство годится как control-образец «карта в PC/SC, но не носитель CSP» рядом с
[JaCarta IDProtect](jacarta-idprotect.md), где вывод такой же, а причина другая (там
TERMINATED-апплет, здесь — чужой стандарт карты).
