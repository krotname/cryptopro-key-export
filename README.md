# CryptoPro Key Export

Утилита для экспорта **собственных** ключевых контейнеров КриптоПро с Рутокена и снятия
запрета на экспорт закрытого ключа. Предназначена для владельца ключей: резервное
копирование, миграция контейнера, конвертация в PKCS#12.

Собрана из двух механизмов:

1. **Снятие контейнера с Рутокена** — через COM-компонент `rtCOMLite.rtContext`
   (порт логики утилиты Контура «Проверка Рутокенов» / `tokens.hta`). Читает файловую
   память токена напрямую, минуя КриптоПро CSP, поэтому запрет на экспорт ключа
   на уровне CSP не мешает снять 6 файлов контейнера (`*.key`).
2. **Снятие запрета на экспорт** — вызов КриптоПро `p12utility --cprepair --keyexport`
   (перезаписывает `header.key`, помечая ключ экспортируемым). Сертификат для операции
   извлекается из контейнера автоматически через CryptoAPI
   (`CryptGetKeyParam(KP_CERTIFICATE)`), пока токен вставлен.

## Полный конвейер

```
Рутокен (неэкспортируемый ключ)
   │  rtCOMLite: SelectMF → EnumFiles → ReadBinary
   ▼
папка с контейнером (name/header/primary/masks/primary2/masks2 .key)
   │  CryptoAPI: CryptAcquireContext → CryptGetUserKey → CryptGetKeyParam(KP_CERTIFICATE)
   ▼
cert_exchange.cer / cert_signature.cer
   │  p12utility --cprepair --container_folder . --cert … --keyexport
   ▼
экспортируемый файловый контейнер (header.key вырастает до ~3 КБ)
   │  установка в CSP: копия папки в хранилище HDIMAGE (имя берётся из name.key)
   ▼
контейнер виден КриптоПро и работает без токена
   │  certmgr -install … && certmgr -export -pfx
   ▼
PKCS#12 (.pfx) — сертификат вместе с закрытым ключом
```

На двухключевом Rutoken Lite GUI автоматически делает две одноключевые
HDIMAGE-копии: `[обмен]` и `[подпись]`. Это обходит дефект `p12utility 4.0.8`,
при котором один общий заголовок показывал оба бита `CRYPT_EXPORT`, но реальный
`certmgr -export -pfx` отвечал `NTE_BAD_KEY_STATE`. Обе копии ставятся в CSP и
выгружаются в отдельные PFX; для подписной копии `topfx` сам выбирает `AT_SIGNATURE`.

Проверить, что запрет действительно снят, можно в любой момент: программа читает
права ключа (`KP_PERMISSIONS`) и показывает, взведён ли флаг `CRYPT_EXPORT`.

## На каких носителях снимается закрытый ключ

Главное различие — **где физически лежит закрытый ключ**. Если в файловой памяти носителя
(шесть `*.key`), его можно прочитать мимо CSP, и «неэкспортируемость» (флаг в `header.key`) не
мешает — в этом весь смысл инструмента. У Рутокен S файлы отдаёт `rtCOMLite`; у Рутокен **Lite**
та же файловая память через `rtCOMLite` не видна, но читается на уровне **APDU** (см. ниже), а
дальше закрытый ключ восстанавливается офлайн. Если же ключ обслуживается в **чипе** (Рутокен ЭЦП,
`CKA_EXTRACTABLE=false`), файловой памяти с `*.key` нет вовсе и снять ключ нельзя.

| Носитель | Где ключ | Бэкап **закрытого** ключа | Статус проверки |
|----------|----------|---------------------------|-----------------|
| **Рутокен S** / старые | файловая память | ожидается ✅ | **не проверено на живом устройстве** — путь заложен, но e2e не прогонялся (нужен Рутокен S) |
| **Рутокен Lite** | файловая память (смарт-карта) | **снимается ✅ (по APDU)** | **проверено e2e** (15.08.2026, fw 8.0): GUI увидел три подключённых токена, снял выбранный напрямую созданный неэкспортируемый двухключевой контейнер, создал обменную и подписную HDIMAGE-копии, установил обе в CSP и выгрузил оба PFX через `certmgr` (2× code 0; OpenSSL видит MAC, keybag и certificate bag). Офлайн-разбор также даёт `d`, и `d·G == Q` совпадает с сертификатом. Разбор — [docs/apdu/rutoken-lite-fw9.md](docs/apdu/rutoken-lite-fw9.md) |
| **Рутокен ЭЦП / ЭЦП 2.0** | чип смарт-карты | нет ❌ | живой токен (12.08.2026, fw 23.02): `rtCOMLite` 19 папок / 0 файлов; PKCS#11 `CKA_EXTRACTABLE=false` (аппаратный флаг чипа); `certmgr -export -pfx` и `csptest -keycopy` → `0x8009000b` |
| **Рутокен ЭЦП 3.0** | чип смарт-карты (ФКН) | нет ❌ | **проверено прямым опытом** (13.08.2026, fw 30.02): на токене создан контейнер с двумя **неэкспортируемыми** ГОСТ-ключами (`KP_PERMISSIONS` без `CRYPT_EXPORT`), ни один применимый путь не сработал — `rtCOMLite` файлов контейнера не дал (смарт-карточный носитель утилита не обходит вовсе), `csptest -keycopy` токен→диск и `certmgr -export -pfx` → `0x8009000b`, команда `export` → 0 контейнеров. PKCS#11 к контейнеру CSP неприменим (объектом не становится); неизвлекаемость чипа подтверждена отдельно, на своей PKCS#11-паре (`CKA_NEVER_EXTRACTABLE=true`, `C_WrapKey` → `CKR_KEY_NOT_WRAPPABLE`). Плюс носитель — ФКН, ключ с диска на него не пишется (`0x80090029`) |
| **JaCarta PRO** (Аладдин Р.Д.) | смарт-карта, **пассивный носитель** | **снимается ✅ (по APDU)** | **проверено байтово** (13.08.2026, JaCarta PRO fw 1.01, PIN от владельца, свой контейнер с ключом на носителе). Штатные пути дают отказ **на уровне политики CSP**, а не карты: `csptest -keycopy`/`certmgr -export -pfx` → `0x8009000b`, PKCS#11 (`jcPKCS11-2.dll`) — 0 объектов, rtCOMLite не показывает. Но APDU-разбор показал пассивность: при подписи `primary.key`+`masks.key` уходят с карты на хост — карта отдаёт их и для неэкспортируемого ключа. У неэкспортируемого `primary.key = SEQUENCE { OCTET STRING, [0] }`, ключ — в поле `[0]`; офлайн-разбор дал `d`, и `d·G == Q` совпало с открытым ключом. Метод и разбор — [docs/apdu/jacarta-pro.md](docs/apdu/jacarta-pro.md) |

Годы появления моделей, их место на рынке РФ и приоритет для тестирования — в
[docs/token-market.md](docs/token-market.md) (сводная таблица).

Разница в доказательности между Lite и ЭЦП принципиальная. На **ЭЦП** ключ помечен аппаратно
неизвлекаемым в самом чипе (`CKA_EXTRACTABLE=false`) — это свойство носителя, снять нельзя. На
**Lite** ключ лежит в **файловой памяти** карты обычным файловым контейнером КриптоПро: раньше
проверенные пути (`rtCOMLite`, PKCS#11, `csptest`) его не отдавали, но КриптоПро работает с Lite
через собственный PC/SC-стек на уровне APDU — и этот путь теперь **исследован и пройден**.
`primary.key` и `masks.key` читаются по APDU мимо CSP, а офлайн-разбор §3.1 даёт закрытый ключ,
проверенный по сертификату (`d·G == Q`). «Неэкспортируемость» на Lite — программный флаг CSP, а не
запрет носителя.

**Важная оговорка ко всей таблице: речь везде о ключе с неснятым запретом на экспорт.**
Ключ, у которого флаг `CRYPT_EXPORT` уже взведён, КриптоПро спокойно копирует с носителя на
диск штатным `csptest -keycopy` — проверено 13.08.2026 и на JaCarta, и на Рутокен Lite: обе
операции код 0, у копий `KP_PERMISSIONS = 0x0013089C`. Ценность инструмента не в этом
случае, а ровно в обратном — когда запрет не снят и CSP отвечает `0x8009000b`. Поэтому проверять
модель нужно на контейнере, ключ которого **сгенерирован на самом носителе**: только он гарантированно
несёт запрет. Готовый рецепт — `token-session\make-token-container.ps1` (лежит в репозитории;
остальное содержимое `token-session\` локальное, там дампы с персданными):

```powershell
pwsh token-session\make-token-container.ps1 -ContainerPath '\\.\<считыватель>\cpxtest' -Password <PIN>
```

Скрипт сам закрывает модальные окна CSP («Выбор ключевого носителя» и «Био ДСЧ»); без него
`csptest -newkeyset -silent` отвечает `0x80090022 NTE_SILENT_CONTEXT`.

**Что доступно независимо от снятия ключа:**

- **сертификат** извлекается прямо с токена без КриптоПро CSP (`token [outDir]` / кнопка
  «Извлечь сертификат»), если он лежит на токене **публичным** объектом PKCS#11
  (`CKA_PRIVATE=false`). Что такие объекты читаются **без ввода PIN**, а объекты с
  `CKA_PRIVATE=true` в той же сессии не видны, проверено на живом железе и на Рутокен ЭЦП 3.0
  (fw 30.02), и на Рутокен Lite (fw 9.02). Практически сертификат чаще оказывается на ЭЦП: у
  виденных Lite объектов PKCS#11 не было вовсе — но хранилище объектов у Lite рабочее, и
  выданный УЦ через PKCS#11 сертификат утилита снимет и с него. Контейнеры, которые кладёт на
  токен сам CSP, объектами PKCS#11 не становятся ни на одной из моделей;
- **диагностика**: тип, серийник, состояние PIN (без траты попыток), список контейнеров;
- **весь конвейер снятия запрета → установка → PFX** работает с контейнером, который уже
  лежит **папкой на диске** (снятый с Рутокен S либо синтетический).

Итог: заменить сам токен **ЭЦП** эта утилита не может — закрытый ключ на нём аппаратно
неизвлекаем, а ЭЦП 3.0 КриптоПро вообще обслуживает как ФКН, куда ключ полагается
генерировать на месте; при утере токена ключ восстановлению не подлежит, порядок обычный —
отзыв сертификата и выпуск нового в удостоверяющем центре. Для **Lite** вопрос APDU **закрыт
положительно**: закрытый ключ снимается чтением файлов контейнера по APDU + офлайн-разбором
§3.1 (проверено байтово, `d·G == Q`); осталась инженерная часть — перенос пути в `Core`. Для
Рутокен S файловый путь заложен и ждёт проверки на живом устройстве.

## Требования (на целевой машине)

- **Windows** + **КриптоПро CSP** (проверено на CSP 5.0 R2, build 15873) — единственное,
  что нужно установить отдельно: это лицензионный продукт, его CryptoAPI-провайдер вшить нельзя.
- **Больше ничего скачивать и доставлять не нужно.** `p12utility.win32.exe` и `rtCOMLite.dll`
  вшиты в приложение и распаковываются в `%LOCALAPPDATA%\CryptoProExport\bundled\<версия>`
  при первом обращении. `rtCOMLite` загружается **без регистрации в системе и без прав
  администратора** (`DllGetClassObject` → `IClassFactory`), устанавливать
  «компонент диагностики Рутокен» не требуется.
- Приложение **32-битное, и это же делает его универсальным**: x86-код идёт на x86, на x64
  (через WOW64) и на ARM64 (через эмуляцию), а вшитый 32-битный `rtCOMLite.dll` грузится
  в процесс только при совпадении разрядности. Сборки x64/arm64 тоже собираются, но для
  работы с Рутокеном им нужен установленный в системе компонент rtCOMLite — программа
  предупредит об этом в отчёте `deps`.
- **Снятие закрытого ключа с токена** через встроенный `rtCOMLite` рассчитано на Рутокен S
  (файловый контейнер в памяти токена). На **Рутокен Lite** и **Рутокен ЭЦП** файловая память через
  rtCOMLite не видна. Для **Lite** это не тупик: контейнер лежит в файловой памяти карты и читается
  на уровне APDU мимо CSP, после чего закрытый ключ восстанавливается офлайн (проверено e2e,
  `d·G == Q`; путь встроен в Core, CLI и GUI). На **ЭЦП** ключ
  аппаратно неизвлекаем. Подробная матрица «модель → снимается ли ключ» и разбор Lite по APDU —
  в разделе [«На каких носителях снимается закрытый ключ»](#на-каких-носителях-снимается-закрытый-ключ)
  и [docs/apdu/rutoken-lite-fw9.md](docs/apdu/rutoken-lite-fw9.md).
- **PKCS#11 берётся из системы, и библиотек может быть несколько.** Каждая показывает только
  носители своего вендора, поэтому программа ищет и загружает все известные — `rtPKCS11ECP.dll`
  (драйверы Рутокен) и `jcPKCS11-2.dll` (JaCarta Unified Client) — и объединяет слоты. Нет ни
  одной или нет части из них — соответствующие носители просто не показываются, ошибки нет.
- **Рутокен ЭЦП при этом полноценно распознаётся** через PKCS#11 (`rtPKCS11ECP.dll` из драйверов
  Рутокена): программа показывает тип токена, серийный номер, состояние PIN (не тратя попыток) и
  контейнеры КриптоПро, а **сертификат извлекает прямо с токена без КриптоПро CSP** — командой
  `token [outDir]` или кнопкой «Извлечь сертификат» (когда CSP сертификат не отдаёт, GUI берёт его
  с токена по PKCS#11). Сам контейнер виден CSP по имени, поэтому проверка прав, установка и
  экспорт в PFX работают с ним как обычно. Известные проверки и что осталось — в [ROADMAP.md](ROADMAP.md).
  Рутокен ЭЦП 2.0 с аппаратным неизвлекаемым ключом выгрузить нельзя в принципе. Остальной конвейер —
  снятие запрета, установка в CSP, экспорт в PFX — работает с контейнером, который уже лежит папкой на диске.

Проверить готовность окружения одной командой:

```
CryptoProExport.exe deps
```

## Языки интерфейса

Интерфейс, подсказки и сообщения переведены на 20 языков:

`ar` العربية · `bn` বাংলা · `de` Deutsch · `en` English · `es` Español · `fa` فارسی ·
`fr` Français · `hi` हिन्दी · `id` Bahasa Indonesia · `it` Italiano · `ja` 日本語 ·
`ko` 한국어 · `pl` Polski · `pt` Português · `ru` Русский · `ta` தமிழ் · `tr` Türkçe ·
`ur` اردو · `vi` Tiếng Việt · `zh-Hans` 中文（简体）

Список собран по числу говорящих (Ethnologue, суммарно L1+L2). От верхней двадцатки
он отличается четырьмя заменами: нигерийский пиджин, маратхи, телугу и юэ заменены
на корейский, итальянский, персидский и польский — у них несравнимо больше носителей
за настольным Windows, а именно там работает КриптоПро CSP. Русский оставлен как язык
исходной аудитории продукта.

Язык берётся из системной культуры (`ru-RU` → `ru`, `zh-CN` → `zh-Hans`, `pt-BR` → `pt`),
иначе — английский. Переопределить можно двумя способами:

- выпадающий список **«Язык интерфейса»** в окне — выбор запоминается в
  `%LOCALAPPDATA%\CryptoProExport\language.txt`;
- аргумент `--lang <код>` в любом месте командной строки:
  `CryptoProExport.exe help --lang en`, `CryptoProExport.exe deps --lang de`.

Для `ar`, `ur` и `fa` окно разворачивается справа налево (`RightToLeftLayout`).

Встроенное руководство (кнопка «Справка» и команда `help`) переведено на русский
и английский; остальные языки интерфейса показывают английский текст — 150 строк
связного текста в двадцати версиях стоили бы дороже, чем дают.

Переведено всё, что программа пишет сама, включая лог полного цикла экспорта.
Не переводятся: вывод `p12utility` и `certmgr` (он приходит от КриптоПро),
сообщения исключений .NET и справочник кодов ошибок `NTE_*`/`SCARD_*` — по коду
вида `0x8009000B` ищут в документации вендора, и один язык там полезнее двадцати.

## Сборка

Нужен .NET SDK 10.

```bash
dotnet build CryptoProExport.slnx -c Release -warnaserror
dotnet test  CryptoProExport.slnx -c Release --no-build
```

Портативная сборка — один `.exe`, внутри и .NET, и обе нативные зависимости, и руководство:

```powershell
pwsh build\publish.ps1
```

На выходе `publish\CryptoProExport.exe` (~47 МБ) и его SHA-256 — в папке больше ничего нет.
Тот же файл собирает CI и прикладывает к релизу по тегу `v*`.

## Использование

**Графический интерфейс** — запустить `CryptoProExport.exe` без аргументов.
У каждой кнопки и поля есть всплывающая подсказка: что делает, что для этого нужно
и что получится. Порядок работы:

1. *Обновить список* — показать CSP-контейнеры и все токены из PKCS#11; строка `rtCOMLite` в журнале имеет свой отдельный счётчик.
2. *Экспорт с токена* — снять контейнеры в папку назначения.
3. *Извлечь сертификат* — сохранить `.cer` выбранного контейнера.
4. *Сделать экспортируемым* — полный цикл в один клик.
5. *Проверить ключ* — убедиться, что запрет на экспорт снят.
6. *Установить в КриптоПро* — чтобы снятый файловый контейнер работал без токена; видимость проверяется именно в HDIMAGE, а не по совпадению имени с токеном.
7. *Экспорт в PFX* — выгрузить контейнер в `.pfx` вместе с закрытым ключом.
8. *Журнал* — открыть папку с журналами работы.
9. *Справка* — встроенное руководство: сценарии, кнопки, команды, разбор ошибок.

В лог при запуске выводится, откуда берутся зависимости и виден ли КриптоПро CSP.

**Консоль:**

```
CryptoProExport.exe help
CryptoProExport.exe deps
CryptoProExport.exe list
CryptoProExport.exe token [outDir]
CryptoProExport.exe extractcert <containerName> <outDir>
CryptoProExport.exe checkexport <containerName>
CryptoProExport.exe export <destDir> [pin]
CryptoProExport.exe keyexport <folder> <cert.cer> [pass]
CryptoProExport.exe install <folder> [name]
CryptoProExport.exe installed
CryptoProExport.exe uninstall <folder>
CryptoProExport.exe topfx <containerName> <out.pfx> [password]
CryptoProExport.exe extractkey <folder> <out.pem> [password]  # закрытый ключ в PKCS#8/PEM без CSP
CryptoProExport.exe extractpfx <folder> <out.pfx> <pfxPass> [password] [cert.cer]  # .pfx без CSP, для OpenSSL
CryptoProExport.exe liteexport <reader> <outDir> [pin]  # снять Lite по APDU; extractkey/extractpfx понимают неэкспортируемую форму primary.key
CryptoProExport.exe full <destDir> [cert.cer] [pin]
CryptoProExport.exe --lang <код>          # язык вывода; можно совмещать с любой командой
```

Типичный сценарий без токена под рукой — контейнер уже снят в папку:

```
CryptoProExport.exe keyexport C:\backup\mykey C:\backup\mykey\cert_exchange.cer
CryptoProExport.exe install   C:\backup\mykey "Мой ключ (копия)"
CryptoProExport.exe checkexport "Мой ключ (копия)"
CryptoProExport.exe topfx     "Мой ключ (копия)" C:\backup\mykey.pfx пароль
```

Журналы каждого запуска — в `%LOCALAPPDATA%\CryptoProExport\logs`. Пароли в них не пишутся.

## Происхождение

Логика снятия с токена восстановлена из открытого `tokens.hta` (JScript внутри
NSIS-обёртки `Tokens.exe`, СКБ Контур). `p12utility` — штатная утилита КриптоПро.
`rtCOMLite.dll` — «Библиотека Rutoken COM Lite» компании «Актив» (v1.0.3.1),
распространяемый компонент диагностики Рутокен; вшит в приложение, чтобы его
не приходилось устанавливать отдельно.
Проект переиспользует эти механизмы для законной работы владельца со своими ключами.
