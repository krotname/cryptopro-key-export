# CryptoPro Key Export

Утилита для экспорта **собственных** ключевых контейнеров КриптоПро с пассивных
носителей Рутокен, JaCarta и ESMART и снятия
запрета на экспорт закрытого ключа. Предназначена для владельца ключей: резервное
копирование, миграция контейнера, конвертация в PKCS#12.

Собрана из двух механизмов:

1. **Снятие контейнера с носителя** — прямое чтение файловой памяти по PC/SC APDU для
   Рутокен S, Рутокен Lite, JaCarta LT/PRO и ESMART. Старый `rtCOMLite.rtContext` сохранён как
   совместимый путь для других файловых Рутокенов, но для S не используется: его
   файловые методы нестабильны на непустом носителе. Весь legacy-вызов выполняется в
   отдельном дочернем процессе: порча нативной кучи завершает одну операцию, а GUI/CLI,
   уже записанный журнал и остальные данные приложения остаются живы. APDU минует КриптоПро CSP,
   поэтому запрет на экспорт не мешает снять 6 файлов контейнера (`*.key`).
2. **Снятие запрета на экспорт** — двумя путями. Основной, без КриптоПро вовсе, — команда
   `exportable`: она восстанавливает оба ключа контейнера по `d·G`, взводит бит экспорта в
   `header.key`, пересчитывает имитовставку заголовка и складывает новую папку-контейнер,
   не трогая исходную. Запасной путь — вызов КриптоПро `p12utility --cprepair --keyexport`
   (перезаписывает `header.key` целиком, помечая ключ экспортируемым); сертификат для него
   извлекается из контейнера автоматически через CryptoAPI
   (`CryptGetKeyParam(KP_CERTIFICATE)`), пока токен вставлен.

## Полный конвейер

```
пассивный токен (неэкспортируемый ключ)
   │  PC/SC APDU: список контейнеров → PIN → чтение шести файлов
   ▼
папка с контейнером (name/header/primary/masks/primary2/masks2 .key)
   │  CryptoAPI: CryptAcquireContext → CryptGetUserKey → CryptGetKeyParam(KP_CERTIFICATE)
   ▼
cert_exchange.cer / cert_signature.cer
   │  p12utility --cprepair --container_folder . --cert … --keyexport
   ▼
экспортируемый файловый контейнер (header.key вырастает до ~3 КБ)
   │  установка в CSP: копия папки в хранилище HDIMAGE (имя берётся из name.key)
   ▼
контейнер виден КриптоПро и работает без токена
   │  certmgr -install … && certmgr -export -pfx
   ▼
PKCS#12 (.pfx) — сертификат вместе с закрытым ключом
```

На двухключевом Rutoken Lite GUI автоматически делает две одноключевые
HDIMAGE-копии: `[обмен]` и `[подпись]`. Это обходит дефект `p12utility 4.0.8`,
при котором один общий заголовок показывал оба бита `CRYPT_EXPORT`, но реальный
`certmgr -export -pfx` отвечал `NTE_BAD_KEY_STATE`. Обе копии ставятся в CSP и
выгружаются в отдельные PFX; для подписной копии `topfx` сам выбирает `AT_SIGNATURE`.

Проверить, что запрет действительно снят, можно в любой момент: программа читает
права ключа (`KP_PERMISSIONS`) и показывает, взведён ли флаг `CRYPT_EXPORT`.

## На каких носителях снимается закрытый ключ

Главное различие — **где физически лежит закрытый ключ**. Если в файловой памяти носителя
(шесть `*.key`), его можно прочитать мимо CSP, и «неэкспортируемость» (флаг в `header.key`) не
мешает — в этом весь смысл инструмента. У Рутокен S, Рутокен **Lite**, JaCarta LT/PRO и ESMART файловая
память читается на уровне **APDU**; для Lite дополнительно нормализуется особая обёртка закрытого
ключа. Если же ключ обслуживается в **чипе** (Рутокен ЭЦП), программа его не копирует:
файлового контейнера `*.key` для этого пути нет. Атрибуты `CKA_EXTRACTABLE` и
`CKA_NEVER_EXTRACTABLE` относятся к конкретному объекту ключа и не выводятся из PID, ATR,
строки модели или версии прошивки.

> [!IMPORTANT]
> **У ESMART два независимых типа ключевого хранилища.** В PFX переносится только
> файловый контейнер КриптоПро из пассивного CSP-раздела. Закрытый ключ,
> сгенерированный внутри защищённого чипа через PKCS#11, остаётся аппаратным и
> неизвлекаемым (`CKA_NEVER_EXTRACTABLE=true`). Поэтому поддержка ESMART в этой
> таблице не означает возможность извлечь любой ключ с устройства.

Годы появления моделей, их место на рынке РФ и приоритет для тестирования — в
[docs/token-market.md](docs/token-market.md) (сводная таблица).

Разница между Lite и ЭЦП принципиальная. На **ЭЦП** криптографические операции выполняются
в чипе, и приложение не обещает копирование аппаратного закрытого ключа. Для точного
расходного экземпляра fw 23.02 это подтверждено на собственной RSA-2048 паре: подпись
работает, а чтение и wrap закрытого ключа запрещены. На **Lite** ключ лежит в **файловой памяти** карты обычным файловым
контейнером КриптоПро: раньше
проверенные пути (`rtCOMLite`, PKCS#11, `csptest`) его не отдавали, но КриптоПро работает с Lite
через собственный PC/SC-стек на уровне APDU — и этот путь теперь **исследован и пройден**.
`primary.key` и `masks.key` читаются по APDU мимо CSP, а офлайн-разбор §3.1 даёт закрытый ключ,
проверенный по сертификату (`d·G == Q`). «Неэкспортируемость» на Lite — программный флаг CSP, а не
запрет носителя.

**Важная оговорка ко всей таблице: речь везде о ключе с неснятым запретом на экспорт.**
Ключ, у которого флаг `CRYPT_EXPORT` уже взведён, КриптоПро спокойно копирует с носителя на
диск штатным `csptest -keycopy` — проверено 13.08.2026 и на JaCarta, и на Рутокен Lite: обе
операции код 0, у копий `KP_PERMISSIONS = 0x0013089C`. Ценность инструмента не в этом
случае, а ровно в обратном — когда запрет не снят и CSP отвечает `0x8009000b`. Поэтому проверять
модель нужно на контейнере, ключ которого **сгенерирован на самом носителе**: только он гарантированно
несёт запрет. Готовый рецепт — `token-session\make-token-container.ps1` (лежит в репозитории;
остальное содержимое `token-session\` локальное, там дампы с персданными):

```powershell
pwsh token-session\make-token-container.ps1 -ContainerPath '\\.\<считыватель>\cpxtest' -Password <PIN>
```

Скрипт сам закрывает модальные окна CSP («Выбор ключевого носителя» и «Био ДСЧ»); без него
`csptest -newkeyset -silent` отвечает `0x80090022 NTE_SILENT_CONTEXT`.

**Что доступно независимо от снятия ключа:**

- **сертификат** извлекается прямо с токена без КриптоПро CSP (`token [outDir]` / кнопка
  «Извлечь сертификат»), если он лежит на токене **публичным** объектом PKCS#11
  (`CKA_PRIVATE=false`). Что такие объекты читаются **без ввода PIN**, а объекты с
  `CKA_PRIVATE=true` в той же сессии не видны, проверено на живом железе и на Рутокен ЭЦП 3.0
  (fw 30.02), и на Рутокен Lite (fw 9.02). Практически сертификат чаще оказывается на ЭЦП: у
  виденных Lite объектов PKCS#11 не было вовсе — но хранилище объектов у Lite рабочее, и
  выданный УЦ через PKCS#11 сертификат утилита снимет и с него. Контейнеры, которые кладёт на
  токен сам CSP, объектами PKCS#11 не становятся ни на одной из моделей;
- **заводские PIN**: реестр стандартных значений по моделям (Рутокен, JaCarta/eToken, ESMART) —
  [docs/standard-pins.md](docs/standard-pins.md) и команда `pins`. В GUI PIN подставляется в поле
  автоматически, когда подключён ровно один носитель, драйвер подтвердил заводское состояние его
  PIN и счётчик попыток чист; отправка PIN на карту остаётся явным действием;
- **диагностика**: тип, серийник, состояние PIN (без траты попыток), версия аппаратуры,
  механизм-профиль, список контейнеров и публичные объекты, если они действительно присутствуют;
- **весь конвейер снятия запрета → установка → PFX** работает как с контейнером в папке,
  так и напрямую с выбранными Рутокен S/Lite, JaCarta LT/PRO и ESMART (`tokenfull`).

Итог: заменить сам токен **ЭЦП** эта утилита не может — закрытый ключ на нём аппаратно
неизвлекаем, а ЭЦП 3.0 КриптоПро вообще обслуживает как ФКН, куда ключ полагается
генерировать на месте; при утере токена ключ восстановлению не подлежит, порядок обычный —
отзыв сертификата и выпуск нового в удостоверяющем центре. Для **S, Lite, JaCarta LT/PRO и ESMART**
APDU-вопрос закрыт положительно: production-код читает контейнер напрямую, а полный цикл
на физических S/LT/PRO и двух ESMART доведён до экспортируемой HDIMAGE-копии и PFX.

## Требования (на целевой машине)

- **Windows** + **КриптоПро CSP** (проверено на CSP 5.0 R2, build 15873): это
  лицензионный продукт, его CryptoAPI-провайдер вшить нельзя.
- Нужен штатный драйвер точного носителя: для Рутокена он предоставляет PC/SC и
  `rtPKCS11*.dll`, для JaCarta — reader и `jcPKCS11-2.dll`, для ESMART — PC/SC и пару
  `isbc_pkcs11_main.dll` + `isbc_esmart_token_mod.dll`. Эти компоненты ставятся
  с драйвером/клиентом производителя и в приложение не вшиваются.
- **Отдельно доставлять служебные утилиты не нужно.** `p12utility.win32.exe` и `rtCOMLite.dll`
  вшиты в приложение и распаковываются в `%LOCALAPPDATA%\CryptoProExport\bundled\<версия>`
  при первом обращении. `rtCOMLite` загружается **без регистрации в системе и без прав
  администратора** (`DllGetClassObject` → `IClassFactory`) только в изолированном дочернем
  процессе. Parent обменивается с ним через отдельные anonymous pipes с версионированными
  length-prefixed сообщениями; stdout/stderr не являются IPC. Устанавливать
  «компонент диагностики Рутокен» не требуется.
- Приложение **32-битное, и это же делает его универсальным**: x86-код идёт на x86, на x64
  (через WOW64) и на ARM64 (через эмуляцию), а вшитый 32-битный `rtCOMLite.dll` грузится
  в процесс только при совпадении разрядности. Сборки x64/arm64 тоже собираются, но для
  legacy-пути rtCOMLite им нужен установленный в системе компонент той же разрядности —
  программа предупредит об этом в отчёте `deps`. Прямые APDU-бэкенды S/Lite/LT/PRO/ESMART от
  rtCOMLite не зависят.
- **Снятие закрытого ключа с токена** для Рутокен S/Lite, JaCarta LT/PRO и файлового CSP-раздела
  ESMART идёт по PC/SC APDU;
  токен при чтении не изменяется. Для PRO ожидаемый ATR ещё раз проверяется через
  `SCardGetAttrib` на том же открытом PC/SC handle до первой APDU и передачи PIN.
  На **ЭЦП** ключ
  аппаратно неизвлекаем. Подробная матрица «модель → снимается ли ключ» и разбор Lite по APDU —
  в разделе [«На каких носителях снимается закрытый ключ»](#на-каких-носителях-снимается-закрытый-ключ),
  а также в [docs/apdu/rutoken-lite-fw9.md](docs/apdu/rutoken-lite-fw9.md),
  [docs/hardware/jacarta-lt.md](docs/hardware/jacarta-lt.md) и
  [docs/apdu/jacarta-pro.md](docs/apdu/jacarta-pro.md).
- **PKCS#11 берётся из системы, а если её там нет — из вшитой копии.** Каждая библиотека
  показывает только носители своего вендора, поэтому программа ищет и загружает все известные —
  `rtPKCS11ECP.dll`, legacy `rtPKCS11.dll` для Рутокен S, `jcPKCS11-2.dll` для JaCarta и
  `isbc_pkcs11_main.dll` для ESMART — и объединяет слоты. Для ESMART entry module считается
  доступным только вместе с `isbc_esmart_token_mod.dll` той же разрядности в том же каталоге.
  Три из них вшиты в exe и распаковываются при первом обращении, так что смарт-карточный
  носитель читается и на машине без драйверов; системная копия всегда идёт первой, потому что
  соответствует установленному драйверу по версии. Рутокен S — исключение: `rtPKCS11.dll`
  импортирует `rtAPIi.dll`/`rtLib.dll` из пакета драйверов, без которого носитель не появится
  и в PC/SC, поэтому его берут только из системы.
  Нет одной или части библиотек — соответствующие носители просто не показываются, ошибки нет.
  Проверка ESMART — в [docs/hardware/esmart-usb64k.md](docs/hardware/esmart-usb64k.md).
- **Рутокен ЭЦП при этом диагностируется** через PKCS#11 (`rtPKCS11ECP.dll` из драйверов
  Рутокена): программа показывает тип, серийный номер, состояние PIN без траты попыток,
  аппаратную версию и профиль фактически объявленных механизмов. **Публичный сертификат** можно
  сохранить прямо с токена без КриптоПро CSP командой `token [outDir]` или кнопкой «Извлечь
  сертификат», но только если такой объект действительно есть. Аппаратный закрытый ключ программа
  не копирует и не обещает экспортировать; PID/model/ATR не считаются доказательством поколения.
  Проверка fw 23.02 — [docs/hardware/rutoken-ecp-fw23.md](docs/hardware/rutoken-ecp-fw23.md).
  Остальной конвейер —
  снятие запрета, установка в CSP, экспорт в PFX — работает с контейнером, который уже лежит папкой на диске.

Проверить готовность окружения одной командой:

```
CryptoProExport.exe deps
```

## Лицензирование

Операции экспорта закрытого ключа (`export`, `full`, `keyexport`, `extractkey`, `extractpfx`,
`liteexport`, `topfx`) требуют **действительной лицензии** — без неё они не выполняются
(жёсткий гейт). Диагностика (`deps`, `list`, `checkexport`, `token`, `installed`, `extractcert`),
установка лицензии и справка доступны всегда.

Продукт лицензируется сервером активации **license-server** (продукт `cryptoexport`). Модель
двухслойная: короткий **код активации** обменивается онлайн на подписанный **файл лицензии**
(compact JWS, ES256), который затем проверяется **офлайн** вшитым в программу публичным ключом
(`kid = cryptoexport-2026`). Сеть при проверке не нужна, домен не важен — доверие в ключе, а не в TLS.

Лицензия привязана к **этой машине**: её отпечаток (`sha256:<hex>` от стабильного идентификатора
установки; сырой идентификатор не передаётся и не логируется) показывает команда `fingerprint`
и строка статуса при запуске.

```
CryptoProExport.exe fingerprint            # сообщите этот отпечаток при выдаче лицензии
CryptoProExport.exe license мой.jws        # проверить для этой машины и установить
CryptoProExport.exe license status         # текущий статус
```

В GUI то же делает кнопка **«Лицензия…»**. Установленная лицензия хранится в
`%LOCALAPPDATA%\CryptoProExport\license.jws`. Пока REST-эндпоинт активации не развёрнут, файл
лицензии выпускается офлайн тем же сервером (`keytool issue-license --pid cryptoexport
--kid cryptoexport-2026 --key <ключ> --fp sha256:<hex> --seats 1`).

При отказе GUI и CLI показывают локализованную структурированную причину: неверный формат
или подпись, другой продукт, платформа, отпечаток машины либо истёкший срок. Точная техническая
диагностика верификатора остаётся только в файле журнала сеанса и не попадает в видимый вывод.

## Языки интерфейса

Интерфейс, подсказки и сообщения переведены на 20 языков — полностью на момент 1.7.0.
Строки, добавленные позже (в 1.8.0 их заметно: поиск по списку, подписи групп кнопок,
объяснение пустого списка, новые причины отказа), во всех локалях остаются русскими —
см. правило ниже. Список языков:

`ar` العربية · `bn` বাংলা · `de` Deutsch · `en` English · `es` Español · `fa` فارسی ·
`fr` Français · `hi` हिन्दी · `id` Bahasa Indonesia · `it` Italiano · `ja` 日本語 ·
`ko` 한국어 · `pl` Polski · `pt` Português · `ru` Русский · `ta` தமிழ் · `tr` Türkçe ·
`ur` اردو · `vi` Tiếng Việt · `zh-Hans` 中文（简体）

Список собран по числу говорящих (Ethnologue, суммарно L1+L2). От верхней двадцатки
он отличается четырьмя заменами: нигерийский пиджин, маратхи, телугу и юэ заменены
на корейский, итальянский, персидский и польский — у них несравнимо больше носителей
за настольным Windows, а именно там работает КриптоПро CSP. Русский оставлен как язык
исходной аудитории продукта.

Язык берётся из системной культуры (`ru-RU` → `ru`, `zh-CN` → `zh-Hans`, `pt-BR` → `pt`),
иначе — английский. Переопределить можно двумя способами:

- выпадающий список **«Язык интерфейса»** в окне — выбор запоминается в
  `%LOCALAPPDATA%\CryptoProExport\language.txt`;
- аргумент `--lang <код>` в любом месте командной строки:
  `CryptoProExport.exe help --lang en`, `CryptoProExport.exe deps --lang de`.

Для `ar`, `ur` и `fa` окно разворачивается справа налево (`RightToLeftLayout`).

Встроенное руководство (кнопка «Справка» и команда `help`) переведено на русский
и английский; остальные языки интерфейса показывают английский текст — 150 строк
связного текста в двадцати версиях стоили бы дороже, чем дают.

Переведено всё, что программа писала сама на момент 1.7.0, включая лог полного цикла
экспорта. Дальше набор языков не расширяется и **новые строки добавляются только
по-русски**: перевод каждого нового ключа на двадцать языков стоит дороже пользы, поэтому
он отложен до отдельного прохода. Практически это значит, что в не-русской локали свежая
надпись какое-то время будет русской — «перевод отстаёт», а не «строка потерялась».
Не переводятся: вывод `p12utility` и `certmgr` (он приходит от КриптоПро),
сообщения исключений .NET и справочник кодов ошибок `NTE_*`/`SCARD_*` — по коду
вида `0x8009000B` ищут в документации вендора, и один язык там полезнее двадцати.

dotnet build CryptoProExport.slnx -c Release -warnaserror
dotnet test  CryptoProExport.slnx -c Release --no-build
```

Портативная сборка — один `.exe`, внутри и .NET, и обе нативные зависимости, и руководство:

## Использование

**Графический интерфейс** — запустить `CryptoProExport.exe` без аргументов.
У каждой кнопки и поля есть всплывающая подсказка: что делает, что для этого нужно
и что получится. Кнопка, которой выбранная в списке строка не подходит, погашена, а
причина дописана в её же подсказке («сейчас недоступно, потому что …») — так видно
заранее, а не сообщением в журнале после нажатия. Кнопки разложены по группам, и слева
от каждой строки написано, к чему она относится: «Список», «Шаги» (порядок работы),
«Результат» (какой файл получится) и «Служебное». Постоянное поле в окне одно — PIN:
папку назначения спрашивает сам экспорт, а язык интерфейса выбирается кнопкой «Язык…»
один раз. Над списком есть поле «Поиск» — оно фильтрует уже собранные строки по любой
колонке без учёта регистра, обход при этом не повторяется.

Видимый журнал по умолчанию показывает обычный рабочий поток. Кнопка «Уровень» переключает
подробную диагностику, обычный поток, предупреждения и ошибки; уже полученные строки при этом
не теряются. Файл сеанса всегда содержит все уровни с метками `DEBUG`, `INFO`, `WARN`, `ERROR`.

Порядок работы:

1. *Обновить список* / `list` — показать CSP-контейнеры и токены из PKCS#11.
   В окне у списка четыре колонки: «Расположение» (где носитель), «Способ чтения»
   (`CSP`, `PKCS#11`, `APDU`, `PC/SC`, `rtCOMLite`), «Контейнер» и «Детали».
   Клик по заголовку сортирует по колонке; третий клик возвращает порядок обхода.
   В командной строке способ чтения по-прежнему написан в самой строке (`[APDU]`).
2. *Экспорт с токена* — снять контейнеры в папку, которую спросит сам экспорт.
3. *Извлечь сертификат* — сохранить `.cer` выбранного контейнера.
4. *Сделать экспортируемым* — полный цикл в один клик.
5. *Посмотреть контейнер* — показать имя, расположение, сведения и состояние
   экспортируемости обоих ключей (`KP_PERMISSIONS`).
6. *Установить в КриптоПро* — чтобы снятый файловый контейнер работал без токена;
   видимость проверяется именно в HDIMAGE, а найденный сертификат привязывается к
   точной HDIMAGE-копии. В списке она показывается отдельно от одноимённого токена.
7. *Сохранить в PFX…* — собрать `.pfx` с закрытым ключом. Способ спрашивается в диалоге:
   через certmgr КриптоПро из выбранной строки либо без CSP из папки снятого контейнера.
   Оба варианта создают файл, который импортируется обратно в КриптоПро.
   Недоступный сейчас способ в диалоге погашен, и рядом написано почему.
8. *Уровень* — отфильтровать видимый журнал по подробности и важности.
9. *Журнал* — открыть папку с журналами работы.
10. *Справка* — встроенное руководство: сценарии, кнопки, команды, разбор ошибок.

Обратный CSP-free путь доступен в CLI: `restore` принимает незашифрованный PKCS#8
(DER или PEM) и обязательный сертификат X.509, проверяет алгоритм, кривую и `d·G`,
затем создаёт новый экспортируемый файловый контейнер. Результат строится во временной
папке, повторно читается существующим экстрактором и только после этого атомарно
публикуется по указанному пути; существующий путь не перезаписывается.

В лог при запуске выводится, откуда берутся зависимости и виден ли КриптоПро CSP.
`deps` также проверяет PnP-present устройства class `SmartCardReader`: reader с не
запустившимся драйвером (например, Code 10) больше не теряется из диагностики вслед за
PC/SC. PnP-present не доказывает физическое подключение: так же учитывается виртуальный или
non-USB reader. Полный PnP Instance ID, описания и имена не выводятся — для USB остаются
только безопасные VID/PID, PnP problem code и status.
Проверенный случай ESMART описан в
[docs/hardware/esmart-token-code10.md](docs/hardware/esmart-token-code10.md).

CryptoProExport.exe fingerprint           # отпечаток этой машины (для получения лицензии)
CryptoProExport.exe license [file|status] # установить файл лицензии (.jws) или показать статус
CryptoProExport.exe --lang <код>          # язык вывода; можно совмещать с любой командой
```

Для проверенного eToken PRO с профилем PRO параметр `--container jacartapro_XX` обязателен. Точный technical id
копируется из строки `[APDU ...]` команды `list`; пользовательское имя контейнера не
принимается. Это гарантирует, что защищённые файлы читаются только у одного явно
выбранного индекса. Для прежних поддержанных моделей без `--container` сохраняется
пакетный режим, а с параметром можно адресно выбрать один контейнер.
Глобальные команды `export`/`full` и GUI без выбранной APDU-строки при подключённой PRO
останавливаются до protected read: используйте адресную команду либо выберите точную
строку контейнера в GUI.

Типичный сценарий без токена под рукой — контейнер уже снят в папку:

```
CryptoProExport.exe exportable C:\backup\mykey C:\backup\mykey-exp
CryptoProExport.exe install    C:\backup\mykey-exp "Мой ключ (копия)"
CryptoProExport.exe checkexport "Мой ключ (копия)"
CryptoProExport.exe topfx      "Мой ключ (копия)" C:\backup\mykey.pfx пароль
```

`exportable` не нужны ни КриптоПро CSP, ни `p12utility`, и запрет снимается сразу с обоих
ключей контейнера — в отличие от `keyexport`, который за вызов правит один ключ. Прежний путь
через `p12utility` остаётся рабочим запасным вариантом:

```
CryptoProExport.exe keyexport C:\backup\mykey C:\backup\mykey\cert_exchange.cer
```

Журналы каждого запуска — в `%LOCALAPPDATA%\CryptoProExport\logs`. Пароли в них не пишутся;
уровень каждой строки записывается независимо от фильтра в окне.

## Происхождение

Логика снятия с токена восстановлена из открытого `tokens.hta` (JScript внутри
NSIS-обёртки `Tokens.exe`, СКБ Контур). `p12utility` — штатная утилита КриптоПро.
`rtCOMLite.dll` — «Библиотека Rutoken COM Lite» компании «Актив» (v1.0.3.1),
распространяемый компонент диагностики Рутокен; вшит в приложение, чтобы его
не приходилось устанавливать отдельно.
Проект переиспользует эти механизмы для законной работы владельца со своими ключами.
